## 三．选题

### 3.1 系统简介

本作品是一款运行于 Android 平台的**像素填空（Fill-a-Pix）逻辑解谜游戏**，属于康思谜题（Conceptis Puzzles）系列中的经典品种。游戏为玩家呈现一个带数字提示的方格棋盘：每个数字表示**以该格为中心的 3×3 区域内需要涂黑的格子数量**。玩家通过纯逻辑推理，逐格确定"涂黑"与"留白"，最终把整个棋盘还原成一幅完整的像素画（红心、笑脸、蝴蝶、苹果、小房子、小鱼、星星、皇冠、月亮、火箭等）。

系统包含以下能力：

- **10 个内置关卡**：尺寸从 10×10 递进到 28×28，分简单 / 中等 / 困难三档难度，每关谜面均经过算法校验**有且仅有唯一解**；服务端另有**即时生成**的在线题库与每日一题（同样每题校验唯一解）；

- **完整的游戏生命周期**：邮箱验证码登录（或游客离线进入）→ 首页（在线入口 + 模式选择 + 关卡网格）→ 游戏页（推理、计时、结算）→ 在线题库 / 排行榜 / 对战大厅；

- **联网能力**：游戏从网络获取（在线题库按难度分档、每日一题全服同题）、单题排行榜（每人最优成绩）、**网络对战 2~4 人**（WebSocket 房间、服务器权威计时与判名次）与**蓝牙双人对战**（RFCOMM 直连，无需服务器）；

- **沉浸式棋盘交互**：智能双向涂黑笔（一支笔完成涂与擦）、拖动连涂、双指缩放平移、精准的指针类型过滤（鼠标滚轮 / 右键不误触发）；

- **笔划级撤销 / 重做**：一条拖动笔划 = 一步撤销，操作历史完整可回溯；

- **显式错误检查 / 一键补齐 / 参考答案**三级辅助体系，兼顾"不打扰"与"救急"；

- **自由 / 限时双模式**、**通关进度与额度按账号持久化**；

- **提示下一步**：基于求解器推导当前盘面"纯逻辑即可推出"的确定格并高亮，把求解器能力反哺给玩家；

- **配套 Python 工具链**：关卡图案渲染核对、稀疏提示生成、唯一解批量校验，形成"设计—生成—校验—入库"的关卡工业化流程。

### 3.2 为什么选择这个游戏（选题理由）

1. **规则极简，推理极深**。Fill-a-Pix 的规则一句话就能讲清（3×3 窗口计数），但求解需要综合运用排除法、区域分割、边界推理等多种逻辑手段，"易学难精"的曲线非常适合做成闯关制游戏，也让"算法解题"（评分点 1）有真正的用武之地。

2. **规则理解可被严格验证**（评分点 2、5）。Fill-a-Pix 的规则是**纯数学约束**——提示数字、答案矩阵、解的唯一性都可以被程序精确表达和验证。我们的每关谜面都由求解器（约束传播 + 回溯）证明唯一解，"每道游戏是否确定唯一解"这一评分点不是靠人工检查，而是由单元测试在每次构建时自动把关。

3. **具备游戏自动生成的完整管线**（评分点 3）。本项目实现了"答案像素图 → 提示推导 → 贪心去提示 → 唯一解校验 → 稀疏谜面"的全自动生成链路（Kotlin 端 + Python 端各一套），新关卡的制作成本从"手工设计并验证"降低到"画一幅图 + 跑一次脚本"。

4. **结果有画面感，天然适合展示**。数独类谜题的终点是一堆数字，而 Fill-a-Pix 的终点是**一幅像素画**——通关瞬间棋盘揭晓完整图案并撒花庆祝，游戏性和观赏性兼备，答辩演示效果好。

5. **工程结构有代表性**。该项目体量适中但覆盖面广：算法层（求解器）、状态层（笔划 / 双栈）、渲染层（Canvas 自绘）、手势层（多指针识别）、网络层（Retrofit + WebSocket）、服务端（FastAPI + SQLite）、会话与鉴权（邮箱验证码）、多线程（协程 / 线程池 / 后台服务）、传感器（摇一摇重置）、广播（网络状态监听）、持久化（SharedPreferences + SQLite）、主题系统（Material 3 恒定深色）、单元测试（纯 JVM）、开发工具链（Python），是一个"五脏俱全"的中小型项目，能有效锻炼分层设计与工程化能力。

### 4.3 核心用例（文字用例图）

系统主要角色为**注册玩家**与**游客**，核心用例及其关系如下：

- 注册玩家：邮箱验证码登录（包含"获取验证码""校验验证码""校验令牌"三个子用例）→ 进入首页 → 选模式 / 选关卡 → 涂格推理（涂黑 / 清除 / 留白 / 连涂 / 缩放）→ 撤销 / 重做 → 检查错误 / 一键补齐 / 提示下一步 / 看参考答案（扩展用例）→ 通关结算 → 解锁下一关；在线侧另有"玩每日一题""浏览在线题库""查看排行榜""创建/加入对战房间"四个扩展用例；

- 游客：跳过登录直接进入首页，仅可玩内置关卡（离线用例），随时可"切换账号"回到登录用例；

- 服务端（系统用例）：发送验证码邮件、校验验证码并签发令牌、即时生成并校验关卡唯一解、裁决对战名次与计时、聚合排行榜；作为外部参与者与客户端交互；

- 计时器（限时模式）作为系统用例与"涂格推理"并发，超时触发"失败结算"。

其中"涂格推理"是最核心用例，其主成功场景为：玩家选中涂黑笔 → 在空白格按下（涂黑）→ 拖动经过多个格子（连续涂黑）→ 抬起（笔划提交入撤销栈）；扩展场景为：按下时已有第二指落下（取消笔划）、落在已黑格（本笔变为清除方向）、棋盘非交互（通关 / 超时后冻结）。

### 5.4 数据库设计

本系统的持久化数据分成两侧：**客户端**只存"这个账号在本机玩到哪了"，数据量小、私人性强，用 Android 轻量键值存储 **SharedPreferences**；**服务端**要存账号、令牌、验证码、题库、每日一题映射与全部通关成绩（跨设备共享、需要对战与排行榜聚合查询），采用 **SQLite** 关系数据库。以下按概念 / 逻辑 / 物理三层描述。

#### 5.4.1 概念设计（E-R 模型）

系统涉及五个实体、四条联系：

- **实体：用户（User）**——属性：用户编号、邮箱（登录身份，唯一）、昵称、注册时间；

- **实体：关卡（Puzzle）**——属性：关卡编号（服务端生成的在线关为负整数，与内置关的正 id 天然分区）、名称、难度、行数、列数、提示矩阵、答案矩阵、来源（题库 / 每日）、创建时间；

- **实体：通关记录（SolveRecord）**——属性：记录编号、关卡编号、用户编号、用时、来源（单人 single / 对战 race）、完成时间；

- **实体：对战房间（Room）**——属性：房号、房主、阶段（lobby / racing / settled）、当前题目、起跑时刻、名次表。房间为**全内存结构**，不落库（进程重启即失效，符合"临时对局"语义）；

- **实体：验证码（Otp）**——属性：编号、邮箱、验证码哈希、创建时间、过期时间、是否已用、失败次数。它不直接关联用户——**验证码属于"尚未证明身份的邮箱"**，校验通过后才创建 / 取回用户行，这是本设计与其它实体最大的概念差异。

- **联系：通关（Solve）**——用户 ↔ 关卡 **m:n**（一个用户可通关多题，一题可被多个用户通关），属性为用时、来源、完成时间；"每题每人取最优成绩"即在该联系上按用户分组取 `MIN(用时)`；

- **联系：每日映射（DailyMap）**——日历日 ↔ 关卡 **1:1**（同一天全服同题，由日期作种子的确定性生成保证）；

- **联系：持有令牌（Token）**——用户 ↔ 令牌 **1:n**（同一账号可在多设备登录，各自持有独立令牌，过期或登出即删除）；

- **联系：索取验证码（RequestOtp）**——邮箱 ↔ 验证码 **1:n**（同一邮箱的历史验证码仅最新一条有效，重发即作废旧码）。

#### 5.4.2 逻辑设计（关系模式与键值模型）

**服务端关系模式**（下划线为主键，*为唯一键）：

- 用户表：Users(<u>user_id</u>, email\*, nickname, created_at)
- 令牌表：Tokens(<u>token</u>, user_id → Users, created_at, expires_at)
- 验证码表：EmailOtps(<u>otp_id</u>, email, code_hash, created_at, expires_at, used, attempts)
- 关卡表：Puzzles(<u>puzzle_id</u>, name, difficulty, rows, cols, clue_json, answer_json, source, created_at)
- 每日映射表：Daily(<u>daily_date</u>, puzzle_id → Puzzles)
- 通关记录表：SolveRecords(<u>record_id</u>, puzzle_id, user_id → Users, duration_ms, source, finished_at)

其中 `SolveRecords.puzzle_id` **刻意不加外键**：对战可由房主选择"内置关"发车，而内置关的数据固化在客户端 `Levels.kt` 中、不在服务端 `Puzzles` 表里，若加外键会直接拒绝这些成绩入库（开发中确实踩到过，见 9.11）。

**客户端键值模型**（进度按账号分片，`prefs` 文件名带 userId 实现同设备多账号隔离）：

| 逻辑表          | 文件名                              | 键（key）              | 值（value）                | 类型                      |
| ------------ | -------------------------------- | ------------------- | ----------------------- | ----------------------- |
| 会话（设备级）      | `xiangsu_auth`                   | `user_id`/`token`/`nickname`/`last_email` | 当前登录账号与上次登录邮箱 | Int / String            |
| 进度（账号级，每账号一文件） | `xiangsu_account_<userId>`       | `completed_levels`  | 已通关内置关 id 集合            | Set\<String>（"1","2",…） |
| 进度（账号级）      | `xiangsu_account_<userId>`       | `online_solved`     | 已通关在线关 id 集合（负 id）      | Set\<String>            |
| 进度（账号级）      | `xiangsu_account_<userId>`       | `fill_quota_used`   | 已消耗的一键补齐次数              | Int（0..6）               |
| 进度（账号级）      | `xiangsu_account_<userId>`       | `last_bonus_day`    | 上次发放每日奖励的日历日            | String（yyyy-MM-dd）      |
| 离线缓存（设备级）    | `xiangsu_level_cache`            | 关卡 id               | 完整关卡 JSON               | String                  |
| 设备设置（设备级）    | `xiangsu_settings`               | `server_url` 等      | 服务器地址、解锁开关、音效 / 摇一摇开关   | String / Boolean        |

内置关的关卡本体不落库：它是静态常量（`Levels.all`）；在线关则由 `PuzzleRepository` 三级缓存（内存 LRU → `xiangsu_level_cache` → 网络），确保"玩过的在线关断网可重玩"。

访问策略：`AccountStore` 用 `MODE_PRIVATE` 打开；写操作一律 `edit().apply()`（异步落盘，避免阻塞主线程）；读操作在构造时一次性加载并映射为 Compose 可观察状态（`mutableStateOf`），首页与游戏页直接订阅状态重组，无重复 I/O。额度上限（6）与每日奖励（+2）为业务常量，固化在 `QuotaLedger` 中并由单元测试覆盖。

**服务端**：单个 SQLite 库文件（默认 `server/xiangsu.db`，可用 `XIANGSU_DB` 环境变量改路径），短连接 + WAL 日志模式：

```sql
PRAGMA journal_mode=WAL;   -- 读写并发:读不阻塞写,适合"边玩边看排行榜"
PRAGMA foreign_keys=ON;    -- 外键约束开启(SolveRecords 除外,见 5.4.2 说明)
```

| 表 | 主键 | 唯一约束 | 索引 | 关键设计点 |
| --- | --- | --- | --- | --- |
| `users` | `user_id` 自增 | `email` | `idx_users_email` | 邮箱即登录身份；`openid` 为历史列，迁移时与 email 同步写入以兼容旧库 |
| `tokens` | `token`（48 位十六进制随机串） | — | `idx_tokens_user` | 有效期 30 天；`user_by_token` 以 `expires_at > datetime('now')` 过滤，过期即失效 |
| `email_otps` | `otp_id` 自增 | — | `idx_otps_email(email, created_at)` | 只存 `sha256(email\|code)`；`used`/`attempts` 支撑单次使用与错码封顶；限流按 `created_at` 时间窗计数 |
| `puzzles` | `puzzle_id`（**负整数**） | — | — | 内置关正 id / 在线关负 id 的命名空间约定，客户端据此区分解锁链 |
| `daily` | `daily_date` | — | — | 日期 → 题号一一映射，保证全服同题 |
| `solve_records` | `record_id` 自增 | — | `idx_records_puzzle`、`idx_records_user` | 排行榜按 `puzzle_id` 分组取 `MIN(duration_ms)`；对战成绩由服务端写入并覆盖自报时长 |

写操作统一走 `execute()`（自动提交），读操作走 `query_one()` / `query_all()`；表结构在服务启动的 lifespan 中 `CREATE TABLE IF NOT EXISTS` 建立，并对旧库执行**幂等迁移**（补 `users.email` 列并建唯一索引、去掉 `solve_records` 的历史外键），使"拿旧库直接启动"不会崩、老账号数据不丢。

**为什么不是 Room / 服务端不用 ORM**：客户端每次只读一个小集合与几个整数，键值存储的读写成本最低；服务端查询都是"分组取最小值"这类简单聚合，直接写 SQL 比引入 ORM 更透明，也更便于在冒烟测试里用纯函数（`compute_board` / `compute_my_best`）验证排序语义。

### 5.5 核心算法概要设计

1. **提示推导（答案 → 谜面）**：`clue[r][c] = Σ answer[r+dr][c+dc]`，dr、dc ∈ {-1,0,1}，越界不计。复杂度 O(rows×cols×9)。

2. **求解器（谜面 → 解集）**：约束传播 + 回溯的深度优先搜索。

   - **传播规则 A（全空）**：提示格窗口内已涂黑数 == 提示值且存在未定格 → 未定格全部置空；

   - **传播规则 B（全涂）**：提示值 − 已涂黑数 == 未定格数 → 未定格全部涂黑；

   - 规则反复应用至不动点；仍有未定格则任选一格分支（涂黑 / 置空）递归；

   - 计数到第 2 个解立即中止（判定"非唯一"），用于把关谜面质量。

3. **稀疏提示生成（谜面美化）**：从全量提示出发，逐个尝试删除提示，删除后调用求解器校验；仍唯一解则保留删除，否则回滚。贪心一轮即可得到大幅精简且唯一解不变的谜面。

4. **笔划机制（交互打包）**：`startStroke() → strokeCell()×N → commitStroke()` 把一次拖动的 N 个格子改动聚合为单个 `Move.Batch` 入撤销栈；`cancelStroke()`（双指落下 / 滚轮误触）整体回滚。

5. **在线关卡生成（服务端，`server/generator.py` + `puzzle_art.py`）**：随机像素画（矩形 / 椭圆 / 三角形叠加）→ 由答案推导全量提示 → 贪心去提示 → **唯一解校验** → 入库。每日一题以"日历日"为随机种子，因此同一天全服生成同一题且可复现；所有在线关（题库、每日、对战选题）都必经唯一解闸门，保证"每道游戏是否确定唯一解"这一评分点不因自动生成而失守。

6. **提示下一步（求解器反哺玩家）**：对当前盘面（已确定的格子作为约束）跑一次约束传播，取"传播中被规则 A/B 唯一确定"的格子作为提示；若传播无法推进且盘面与答案矛盾，则引导玩家先做错误检查。求解器由此从"质量闸门"扩展为"玩家的推理助手"。

7. **对战裁决（`server/rooms.py`）**：房主提交的题目整关 JSON 由服务端缓存为校验基准；选手提交棋盘时**只比对涂黑掩码**（与 `Validator.isSolved` 同构，留白标记不参与）；名次 = 服务器接收序，时长 = 服务器时钟差值，客户端自报的用时一律忽略。蓝牙对局无服务器，改用**双端对称校验**：双方各自校验对方答案掩码并交换用时，排序规则一致即可得到相同胜负结论。

## 六．详细设计

### 6.1 数据模型设计

**格子三态**（`CellState`）：以 Int 值存储，便于 `IntArray` 紧凑表示整盘：

| 枚举            |  值  | 含义     | 棋盘视觉      |
| ------------- | :-: | ------ | --------- |
| UNDECIDED     |  0  | 未决定    | 暖白纸面      |
| FILLED        |  1  | 涂黑     | 深墨紫       |
| MARKED\_EMPTY |  2  | 标记确定留白 | 浅薰衣草 + 圆点 |

**关卡结构**（`Level`）：`id / name / difficulty(简单★/中等★★/困难★★★) / rows / cols / clueGrid(−1 表示无提示) / answerGrid / timedLimitSeconds / cluePositions(稀疏提示坐标集)`，工厂方法 `fromAnswer(...)` 接收答案矩阵与提示位置，内部调用 `PuzzleGenerator` 生成 clueGrid——**谜面是推导产物而非手工数据，天然与答案一致**。

**身份与模式**（`AuthManager.Session` / `GameMode`）：会话为数据类 `Session(userId, token, nickname, email)`，游客会话用负值 userId（-99）与空 token 表示；模式为 FREE / TIMED。均为无状态枚举 / 不可变数据类。

### 6.2 棋盘状态与笔划机制（GameBoard）

```
class GameBoard(rows, cols) {
    cells: IntArray                     // 当前棋盘（三态 Int）
    undoStack / redoStack: ArrayDeque<Move>   // 双指令栈

    // 笔划 API
    startStroke()                       // 开笔：暂存本笔所有改动
    strokeCell(r, c, target): Boolean   // 涂格：目标态相同则跳过；返回棋盘是否变化
    commitStroke()                      // 收笔：非空笔划打包 Batch 压栈（清空 redo）
    cancelStroke()                      // 取消笔划：回滚本笔全部改动（双指误触用）

    undo() / redo() / reset()           // 标准 undo/redo；重置也走栈，可撤销
    applySolution(answer)               // 一键补齐：整批 Batch
}
```

Move 抽象为"一批 (index, 旧值, 新值)"三元组集合（Batch），撤销 = 逆序回写旧值，重做 = 正序回写新值。设计要点：

- **一笔一记录**：拖涂 20 格只占一个栈元素，撤销一步回退整笔；

- **cancelStroke 与 commitStroke 对称**：手势层任何"非正常结束"（双指落下、指针类型不符）都能整体回滚，不留半笔；

- `strokeCell` 返回 Boolean（本格是否真的变化），界面层据此驱动版本号自增，避免无效重组。

### 6.3 提示推导（PuzzleGenerator）

```kotlin
fun clueAt(answer, r, c): Int {
    var n = 0
    for (dr in -1..1) for (dc in -1..1) {
        val rr = r + dr; val cc = c + dc
        if (rr in answer.indices && cc in answer[0].indices && answer[rr][cc] == 1) n++
    }
    return n
}
```

全量提示：每个格子都算 clueAt；稀疏提示：只在 `cluePositions` 集合内的格子放置数字，其余置 −1。规则实现与康思官方 Fill-a-Pix 完全一致（窗口越界裁剪、数字 0\~9）。

### 6.4 求解器（PuzzleSolver）

求解主流程：

```
solve(clues, maxSolutions=2):
  1. 初始化 candidates[r][c] = {0, 1}（每格的可取值域）
  2. loop 约束传播直至不动点：
       对每个提示格 (r,c)：
         covered = 窗口内已确定为 1 的数量
         unknown = 窗口内未确定格数量
         if covered == clue:            规则A → unknown 全部置 0
         if clue - covered == unknown:  规则B → unknown 全部置 1
  3. 若全部格子已确定 → 记录一个解
  4. 否则选一个未定格（启发式：任取），依次假设 1 / 0 递归
  5. 解数达到 maxSolutions 提前终止
```

- **唯一解判定**：`maxSolutions=2`，找到第二个解即返回"非唯一"——生成关卡时的质量闸门；

- **性能**：约束传播先收敛大部分格子，回溯只处理真正歧义的区域，28×28 谜面毫秒级出解；

- 该求解器同时是"算法解题"评分点的直接证据：给定任意合法谜面，程序都能推出全部解。

### 6.5 校验器（Validator）

三类校验相互独立：

| 方法                             | 语义                                                         | 用途      |
| ------------------------------ | ---------------------------------------------------------- | ------- |
| `isSolved(board, answer)`      | 每格 FILLED 状态与答案逐位相等（留白标记不参与）                               | 通关判定    |
| `wrongCells(board, answer)`    | 仅报"已提交但画错"：FILLED≠答案 1，或 MARKED\_EMPTY≠答案 0；UNDECIDED 永不误报 | 🔍 检查错误 |
| `satisfiedClues(board, clues)` | 提示格窗口无未定格且涂黑数 == 提示值                                       | 数字变绿反馈  |

"错误检查默认不打扰"的设计哲学：平时棋盘不显示任何对错信息（防止变相偷看答案），玩家主动请求时才一次性给出精确结果。

### 6.6 棋盘视图与手势（BoardView）

**渲染**：单 `Canvas` 自绘整盘（28×28 也只有一次 draw 调用批次）。绘制顺序：格子底色（四态分色）→ 留白圆点 → 提示数字（0\~9 按数值分色、已满足变绿、涂黑格上白字）→ 错误红 ✗ → 网格线（线宽÷viewScale 保证放大后仍是 1px）→ 装裱外框（随缩放变换）。

**手势（awaitEachGesture 自定义循环）**：

1. `awaitFirstDown(requireUnconsumed=false)` 等待落下；
2. **指针类型过滤**：仅 `PointerType.Touch` 与 `PointerType.Mouse`（且鼠标仅左键）进入笔划流程，中键 / 右键 / 触控笔忽略；
3. 单指：进入笔划采样循环，移动量超过半格步长即换算格子并回调 `onStrokeCell`（快速滑动不断线）；
4. 第二指落下：立即 `onStrokeCancel()`（回滚第一指误涂）并切换到变换手势（缩放 + 平移）；
5. 抬起：`onStrokeEnd()` 提交笔划；
6. 非交互模式（通关揭晓 / 超时冻结）：仅允许查看手势，禁涂。

**缩放体系**：双指捏合（zoom 中心锚定）+ ＋/− 按钮（视口中心锚定）+ 复位按钮；`clampViewOffset` 把平移量约束在"棋盘始终覆盖视口"范围内，杜绝拖飞。

**指针坐标 → 格子下标**：逆变换 `(pos − offset) / scale` 再除以格宽高，全部 O(1)。

### 6.7 游戏页状态管理（GameScreen）

界面状态全部为 Compose 可观察对象：

| 状态                          | 类型                     | 驱动内容                       |
| --------------------------- | ---------------------- | -------------------------- |
| boardVersion                | Int 计数器                | 棋盘 Canvas 重组的唯一触发器（避免整页重组） |
| tool / strokeTarget         | PaintTool / CellState? | 当前笔 + 智能笔的整笔方向             |
| checkedWrong                | Set\<Pair>?            | 检查错误结果（动手即清空）              |
| elapsedSeconds / timedOut   | Int / Boolean          | 计时与超时                      |
| showZoomed / revealedAnswer | Boolean                | 参考答案查看与"看过"标记              |

智能双向笔的方向判定：

```kotlin
PaintTool.FILL -> strokeTarget ?: run {
    val t = if (board[r][c] == FILLED) UNDECIDED else FILLED  // 起笔定向
    strokeTarget = t; t
}
```

`onStrokeBegin` 时 `strokeTarget = null`，本笔第一格落在黑格 → 整笔为"清除"；否则整笔为"涂黑"。撤销依然一步整笔。

**计时**：`LaunchedEffect` + `delay(1s)` 协程自增；限时模式超时置 `timedOut=true` 冻结棋盘并弹失败卡。

**响应式布局**：`BoxWithConstraints` 判定宽 ≥600dp 走"左棋盘 + 右侧栏"，否则竖排紧凑布局（控件压缩至约 130dp 高，棋盘最大化）；结算卡 `heightIn(max = maxHeight−24dp)` + 卡内 `verticalScroll`，任何屏幕不溢出。

### 6.8 账号进度持久化（AccountStore / QuotaLedger）

- **按账号分片**：`AccountStore(context, userId)` 用 `xiangsu_account_$userId` 作为 prefs 文件名，同一设备切换账号时各账号的通关集合、额度、在线关记录完全隔离；`AppGraph` 维护 `userId → AccountStore` 的注册表，避免重复构造与重复 I/O。

- `completedLevels: Set<Int>`（仅内置关，`levelId > 0`）、`onlineSolved: Set<Int>`（在线关，负 id，只做"玩过"标记不参与解锁）、`fillQuotaUsed: Int`、`lastBonusDay: String?` 均为 `mutableStateOf`，首页关卡网格与游戏页额度按钮实时联动；

- `markCompleted` 幂等（重复通关不重复写，在线关 id 直接忽略）；`pruneCompleted(validIds)` 在账号初始化时清理已删除关卡的孤儿 id；

- **每日登录奖励**：额度规则抽成纯对象 `QuotaLedger`（不碰 SharedPreferences，可直接 JVM 单测）——`applyDailyBonus(fillUsed, lastBonusDay, today)` 仅在**跨日**时发放 `+2`（上限 6），同日重复登录或自动续登不重复发放；之所以从"每次登录 +2"改成"每日 +2"，是因为**会话持久化后冷启动会自动续登**，"每次登录"在真实使用中会退化成形同虚设甚至刷额度；

- `useFill()`：消耗一次额度，用尽返回 false（按钮已灰化）；

- 顺序解锁：`isUnlocked(id) = id > 0 && (id == 1 || (id - 1) in completedLevels)`，在线关与游客同样走这条判定；设置页另有"全部解锁"本机开关，供答辩演示直接跳到任意关卡。

### 6.9 登录与会话（AuthManager / LoginRules / ApiClient）

**两步式邮箱验证码登录**的客户端实现：

```
requestEmailCode(email)                       loginWithEmailCode(email, code)
  ① LoginRules.validateEmail 本地校验           ① 校验码为 6 位数字
  ② POST /api/auth/send-code                  ② POST /api/auth/login {email, code}
  ③ 记下 resendAfterSeconds 起倒计时            ③ 成功 → persist(userId, token, nickname, email)
  ④ 若服务端回显 devCode 则直接展示(演示模式)        ④ isNew → 标记"首次登录"，由根导航弹昵称引导
```

- **客户端不生成、不持久化任何验证码**：验证码由服务端生成与校验，客户端只负责"提交用户输入"与"持久化服务端下发的令牌"。账号的稳定性来自服务端 `users` 表里那一行（邮箱唯一），而不是客户端复用的某个 code —— 这一点在旧版"设备级 mock code"设计里是错的（真实凭证都是一次性的，见 9.10）。

- **`LoginRules`**：把邮箱格式校验、验证码输入过滤（只留数字、截断 6 位）、提交可用性、重发倒计时抽成纯逻辑对象，UI 只做渲染 —— 因此这套规则可以在 JVM 上直接单测，也保证了"客户端提示"与"服务端判定"用同一套口径。

- **`ApiClient`**：OkHttp 拦截器在每个请求发出时读取 `AuthManager.session.token` 注入 `Authorization: Bearer`，因此登出 / 401 后旧令牌立即失效；`safe {}` 把 Retrofit 挂起调用的异常统一映射为可直接展示的文案（网络不可达 / 服务端 `{"error": ...}` 文案 / 401 特殊化为 `UnauthorizedException`）；`LocalSettings.serverUrl` 变更后按版本号自动重建 Retrofit 实例。

- **冷启动续登**：`AuthManager.init` 读 `xiangsu_auth` prefs 恢复会话；游客以 `userId = -99`、空 token 表示，`isGuest` 为真时首页隐藏在线入口并展示"游客模式"提示条。

- **服务端**：验证码只存 `sha256(email|code)`、10 分钟过期、单次使用、错 5 次作废、60 秒重发间隔与每小时 / 每天发送上限；发信走标准库 `smtplib`（QQ 邮箱 / 163 授权码），**未配置 SMTP 或投递失败时回退为控制台打印验证码**，保证无外网环境仍可完成登录演示。

### 6.10 对战设计（BattleProtocol / BattleSession / 双传输）

**协议与状态机复用同一套代码**，只在传输层分叉：

```
BattleTransport(接口)           connect / send / close
  ├── NetworkBattleTransport    OkHttp WebSocket → /ws/rooms/{code}?token=…
  └── BluetoothBattleTransport  BluetoothSocket(RFCOMM) 直连，帧带换行分界

BattleSession                  与传输无关的竞速状态机
  帧类型：roomState / choosePuzzle / start / raceStart / progress
         / finish / finished / result / rematch / playerLeft / error / ping / timeSync
```

- **网络对战**：服务端建房（4 位房号，去掉易混字符 `0O1I`）→ 全员连同一房间 → 房主选题（内置 / 每日 / 随机）→ 服务端缓存题目为校验基准并广播 `raceStart` → 竞速中 `progress` 帧按 0.5 秒节流转发用于实时进度条 → `finish` 由服务端比对掩码、按接收序排名、按服务器时钟计时并写榜。

- **断线重进与重赛**：掉线只标记 `connected=False`，席位与进度保留；房主掉线保留宽限期（默认 60 秒）等待重连，超时才解散房间；竞速中重进的未完成者会被重发题目并重置进度（本地棋盘已丢）；`settled` 后房主可 `rematch` 回到 lobby 清空上局状态。

- **服务器时钟校时**：客户端与服务器往返 `timeSync` 帧，按 NTP 思路用往返时延校正得到服务器时刻，竞速计时与名次全部以此为准，客户端改系统时间无法作弊。

- **蓝牙双人对战**：Classic RFCOMM 直连，无需网络与服务器；主机选题发车，双方各自校验对方提交的答案掩码并按用时排序 —— **双端对称校验**保证两端独立算出的胜负结论一致。

### 6.11 视觉主题与共享控件

### 6.12 Python 工具链设计

| 脚本                                         | 输入                                   | 输出                       | 用途                   |
| ------------------------------------------ | ------------------------------------ | ------------------------ | -------------------- |
| `gen_clues.py [关名]`                        | 图案答案                                 | Kotlin `SparseClues` 代码段 | 贪心去提示 + 唯一解校验，生成稀疏提示 |
| `verify_clues.py`                          | `SparseClues.kt` + `gen_clues.py` 图案 | 每关 OK / NOT-UNIQUE       | 全量关卡唯一解回归校验          |
| `gen_audio.py`                             | 合成参数                                 | `res/raw` 音效文件           | 生成点击 / 通关 / 错误音效     |

修改关卡的标准流程：改 `Levels.kt` 图案 → 同步 `gen_clues.py` 中的图案副本 → `verify_clues.py` 找出失效关 → `gen_clues.py <关名>` 重生成 → 提示集贴回 `SparseClues.kt` → `./gradlew testDebugUnitTest` 终审。

工具链刻意保持精简：定稿期间用过的 `render_patterns.py` / `final_patterns.py`（把图案渲染成终端字符画肉眼核对造型）与 `update_clues.py`（把生成结果自动写回 `SparseClues.kt`）已在图案定稿后删除 —— 它们各自携带第 3、4 份图案与绘图原语副本，留着只会与 `puzzle_engine.py` 漂移；“写回”改为把 `gen_clues.py` 的输出直接贴回 `SparseClues.kt`，少一层可能悄悄覆盖线索集的间接层。

工具链与服务端**共用同一份谜题引擎**（`server/puzzle_engine.py` 的求解器与唯一解判定）：服务端 `generator.py` 生成在线关、`tools/` 校验内置关，双方调用的是同一实现，因此"Python 侧认为唯一解"与"Kotlin 侧 `PuzzleSolver` 认为唯一解"是两道独立实现的双保险，而不是同一份代码的自我确认。

### 7.2 关键功能实现

**（1）通关判定与结算**：每次棋盘版本号变化后调用 `Validator.isSolved`；为 true 时冻结棋盘、切换"图片模式"（隐藏提示数字，直接以答案矩阵渲染，避免留白圆点残留在成品画上）、撒花动画 + 结算卡（用时、下一关按钮）。在线关通关额外触发成绩上传（`POST /api/leaderboard/submit`），失败静默不影响本地通关。

**（2）限时模式**：倒计时胶囊常驻 HUD；`timedOut` 触发 `TimeoutOverlay`（红描边卡 + 再来一局 / 返回），本局不写通关进度。

**（3）一键补齐**：`useFill()` 扣额度 → `GameBoard.applySolution(answer)`（一个 Batch，可一步撤销）→ 版本号自增；额度为 0 时按钮灰化并显示"额度不足"。

**（4）检查错误**：`Validator.wrongCells` 返回精确错格集合，Canvas 层红底 + 红 ✗ 渲染；"清除错误格"把错格批量回未定（同样打包成 Batch 可撤销）；玩家任何动手操作自动清空过期的检查结果。

**（5）已满足提示变绿**：每次重组计算 `satisfiedClues` 集合传入 BoardView，提示数字按"满足 → 绿色、涂黑格上 → 白字、其余按数值分色"三级渲染。

**（6）拖动连涂**：手势循环按"半格步长"采样移动事件，把每个途经格子回调 `strokeCell`；由于一条笔划在 `commitStroke` 前不落撤销栈，快速乱拖也只产生一个可撤销单元。

**（7）鼠标环境净化**：`awaitFirstDown` 后检查 `PointerType` 与按钮，仅 Touch / 鼠标左键放行；滚轮事件在自定义手势循环中不消费、不缩放，桌面调试时操作与真机一致。

**（8）关卡数据**：小图（10×10~~16×16）用 ASCII 字符画~~ ~~`art("X.", …)`~~ ~~定义，直观可改；大图（20×20~~28×28）用 `fillRect / fillEllipse / carveEllipse / fillTriangle` 程序化作画（如月亮 = 大圆挖去偏置小圆）。`Level.fromAnswer` 由答案自动生成全量 clueGrid，再叠加 SparseClues 得到稀疏谜面。

**（9）邮箱验证码登录**：登录页为两步式状态机（`LoginStep.EMAIL` / `CODE`）。发码后启动 `LaunchedEffect` 倒计时协程（与 `LoginRules.tick` 同步），验证码输入框在 `onValueChange` 里过滤非数字并截断 6 位，**填满 6 位自动提交**；服务端错误文案（邮箱格式 / 发送太频繁 / 验证码已过期 / 已失效）经 `ApiClient.safe` 原样呈现，用户不需要看错误码。服务端侧验证码入库前先 `sha256(email|code)`，校验用 `secrets.compare_digest` 常量时间比较，消费用 `UPDATE ... WHERE used = 0` 的 `rowcount` 保证并发下也只有一方成功。

**（10）游戏从网络获取**：`PuzzleRepository` 三级缓存（内存 LRU 16 题 → `xiangsu_level_cache` → 网络），命中即返回，未命中才走 Retrofit；服务端 `GET /api/puzzles/{id}` 返回整题（含答案，客户端本地校验用），题库列表只回元信息（不含答案矩阵，避免一次性拉大包）。每日一题按 `content.today_cn()` 的东八区日历日取题，全服同题。

**（11）排行榜**：服务端 `compute_board` 按 `puzzle_id` 分组取每人 `MIN(duration_ms)` 排序（`ORDER BY best ASC, user_id ASC` 保证并列名次稳定），`compute_my_best` 用"比我的最优更快的行数 + 1"反推我的名次；`source` 参数区分单人 / 对战榜单，两榜独立。

**（12）网络对战**：客户端 `NetworkBattleTransport` 用 OkHttp WebSocket 连接 `/ws/rooms/{code}?token=…`，25 秒发一次 `ping` 保活（服务端 90 秒无消息判掉线）；`BattleSession` 解析帧并驱动 Compose 状态，进度帧 0.5 秒节流；服务端在 `finish` 帧里比对涂黑掩码、按接收序排名、按服务器起算时刻计算时长并写入 `solve_records(source='race')`。

**（13）蓝牙双人对战**：`BluetoothBattleTransport` 用 Classic RFCOMM（UUID 固定、主机 `listenUsingRfcommWithServiceRecord` 等待、从机 `createRfcommSocketToServiceRecord` 连接）直连，帧以换行分界；对局结束后双方各自校验对方答案掩码并交换用时，用同一排序规则独立得出结论，两端结果必然一致。

**（14）断网与网络感知**：`NetworkMonitor` 注册 `CONNECTIVITY_ACTION` 广播驱动顶部红条；`ApiClient` 把 `IOException` 统一映射为"无法连接服务器,请检查网络或设置页的服务器地址"，登录页与在线入口因此都有可读的降级路径而不是崩溃或空转。

### 8.4 关卡数据回归校验

`python tools/verify_clues.py` 对全部 10 关输出 `OK (unique, keep)`——即每一关的稀疏提示集在当前答案下仍保证唯一解（该脚本与 Kotlin 单元测试双保险，分别校验 Python 侧与 Kotlin 侧的同源数据）；服务端在线关在生成时同样必须通过 `puzzle_engine` 的唯一解校验，两道闸门使用独立实现。

- 28×28 棋盘（784 格）拖动连涂、双指缩放均无肉眼可感卡顿（单 Canvas 批量绘制 + 版本号局部重组）；

## 九．遇到的问题、解决办法或改进思路

### 9.1 关卡图案：笑脸嘴角方向错误

**问题**：渲染核对时发现第 2 关"笑脸"的嘴巴画成了 ∩ 型（嘴角低、中间高），整体像"皱眉"，与"微笑"的关卡语义相悖。
**解决**：调整 `Levels.kt` 中 art 定义的两行顺序，改为 ∪ 型微笑；图案变化导致原稀疏提示不再唯一解，随即用 `gen_clues.py smiley` 重新生成提示集并写回 `SparseClues.kt`（31→30 个提示），`verify_clues.py` 与单元测试双重确认恢复唯一解。

### 9.2 关卡图案：月亮的孤立杂散像素

**问题**：第 9 关"月亮"（大圆挖去偏置小圆的程序化作画）渲染后在 (5,19)、(19,19) 出现两个**远离月牙主体的孤立像素**——大椭圆在边缘处因浮点舍入填入了 0.98<1 的格子，而挖除椭圆在该处 1.03>1 挖不掉，玩家会看到两个莫名其妙的孤点。
**解决**：把 `carveEllipse` 半径从 7.5 微调到 7.7，让挖除范围完整覆盖填充边缘，孤立像素消失；同步修改 Python 工具副本(`gen_clues.py`)并重新生成 moon 的稀疏提示。**教训**：程序化作画的浮点边界要显式核对，为此我们把"改图案必跑 `verify_clues.py` 唯一解回归 + `CoreLogicTest` 终审"写进工具链标准流程。

### 9.3 图案副本双源同步

**问题**：`Levels.kt`（Kotlin）与 `gen_clues.py`（Python）各存一份图案定义，改了 Kotlin 侧忘了 Python 侧时，`verify_clues.py` 会拿旧答案校验新提示，产生误判。
**解决**：在 `tools/README.md` 与项目 README 中固化"改图案必须同步两处"的标准流程，并在流程末尾追加单元测试终审，杜绝单侧漂移。
**改进思路**：长期方案是让 Python 直接解析 `Levels.kt` 源码提取图案（单一数据源），消除副本。

### 9.4 鼠标滚轮 / 右键误触发笔划

**问题**：桌面调试时鼠标滚轮滚动会沿滚动方向"涂出一条笔划"，右键 / 中键也会起笔，严重干扰操作。
**根源**：手势层 `awaitFirstDown(requireUnconsumed=false)` 不区分指针类型，滚轮产生的事件流被当作拖动处理。
**解决**：在起笔处增加指针类型与按钮过滤（仅 Touch / 鼠标左键放行），拖动循环中再次过滤；并移除此前实验性加入的"滚轮缩放"（滚轮在棋盘上一律无响应）。桌面与真机行为从此完全一致。

### 9.5 涂 / 擦两支笔切换繁琐

**问题**：初版为"涂黑 / 留白 / 清除（橡皮）"三支笔，频繁在涂黑与橡皮间切换，操作路径长。
**解决**：合并为**智能双向涂黑笔**——起笔第一格决定整笔方向（落黑格 = 清除笔，其余 = 涂黑笔），整笔方向一致（数独类 App 的成熟交互范式），一支笔覆盖全部单指操作；笔划机制保证"方向判定"与"一步撤销"互不干扰。

### 9.6 胜利结算弹窗在小屏溢出

**问题**：结算卡内容（标题 + 190dp 像素画 + 数据 + 按钮）总高约 500dp，在小屏 / 横屏下超出屏幕高度，居中布局上下被裁切，观感像"没居中"。
**解决**：改用 `BoxWithConstraints`，卡片 `heightIn(max = maxHeight − 24dp)` 封顶 + 内容 `verticalScroll`，像素画宽度按屏宽 62% 封顶 180dp 自适应；任何屏幕都能完整居中显示。

### 9.7 大棋盘显示区域不足

**问题**：20×20 / 28×28 关卡在竖屏手机上格子过小（底部控件占掉约 310dp），虽然可缩放但默认视野不理想。
**解决**：重排竖屏控件——撤销 / 重做 / 重置改紧凑胶囊、辅助三键合并一行，控件区压缩到约 130dp，棋盘高度增加约 180dp；宽屏（≥600dp）自动切"左棋盘 + 右侧栏"双布局。以 1440×2560 设备实测，16×16 关格子从约 16dp 提升到 21dp。

### 9.8 主题观感不统一（跟随系统亮暗的副作用）

**问题**：浅色模式下棋盘纸面与界面底色接近，玩法区不突出；系统切深色时部分硬编码浅色控件对比度不足。
**解决**：整体转向**恒定深色"深夜画室"主题**——夜幕界面 + 亮纸棋盘的聚光对比，所有颜色收口到 Material 3 色板；系统栏固定浅色图标；游戏观感在任何设备 / 系统外观下保持一致，也更有"游戏氛围"。

### 9.9 构建环境偶发 Kotlin daemon 失败

**问题**：命令行构建偶发 "Kotlin daemon compilation failed"，但构建实际成功（Gradle 自动 fallback）。
**处理**：确认是 daemon 与 JDK 路径的环境问题，不影响结果；必要时 `./gradlew --stop` 重启 daemon 即可。

### 9.10 登录方式：从"微信式一键登录"改为"邮箱验证码"

**背景。** 实验要求写的是"不需要用户名密码登录，要求小程序登录"。我们最初的实现是"微信小程序式授权登录"：客户端生成一个 code，服务端按 `code2session` 流程换 openid 与令牌——在没有微信资质的前提下，整条链路能跑通，但**本质上是自欺**：服务端拿到的 code 是客户端自己编的，`openid` 是 `sha1(code)` 派生的，**服务端从未验证过任何东西**，任何人都能拿任意字符串换到一个账号。

**调研结论（决定放弃真微信登录）。** 我们查证了微信官方文档，确认三件事：

1. **原生 App 的微信登录不是小程序那套接口**。App 走 OAuth2.0 的 `sns/oauth2/access_token`（参数 `code`），而我们代码里写的 `sns/jscode2session`（参数 `js_code`）是小程序专用接口，用移动应用的 AppID 去调只会得到 `40013 invalid appid`；

2. **Android 端"应用必须通过审核才能调起微信"**（官方 Android FAQ 原文），且未上架应用的微信登录有 **100 次/天** 限制（超限报错 `10060`）；移动应用还需要已认证主体、可访问的应用官网（备案主体一致）、App 运行流程图等材料，审核 1–7 个工作日；

3. **客户端"持久化一个 code 反复使用"的写法与真实凭证语义冲突**：真实 code 一次性、10 分钟过期，第二次登录必然 `40163 code been used`。真实场景下身份的稳定性来自服务端持久化的 openid，而不是客户端复用的 code。

结论是：以我们可获得的资质（个人主体、无企业认证、无已上架应用）**无法完成真实微信登录的接入与演示**，而"保留一个假的微信登录"在答辩中是不诚实的。

**解决办法。** 改成**邮箱 + 6 位验证码**登录：真实发信（SMTP）、真实校验（服务端签发令牌）、可离线兜底（未配置 SMTP 或发信失败时验证码打印在服务端控制台，登录流程照常走完）。它满足实验"不需要用户名密码"的原始意图，同时把"登录"这件事做成了**真的**：

| 维度 | 旧:微信式 mock | 新:邮箱验证码 |
| --- | --- | --- |
| 身份凭证来源 | 客户端自编 code，服务端 `sha1` 派生 | 服务端生成 6 位码，SMTP 投递到用户邮箱 |
| 服务端验证 | 无（任意非空 code 都发令牌） | 校验哈希、有效期、单次使用、失败次数、发送频率 |
| 凭证语义 | 设备级固定值，永久有效 | 一次性、10 分钟过期，与真实 OAuth code 语义一致 |
| 可否离线演示 | 可以 | 可以（控制台兜底通道） |
| 诚实性 | 对外宣称"微信登录"但无微信参与 | 宣称与实际一致 |

**顺带修掉的问题**：旧实现里 `AuthManager` 会把 code 存进 prefs 长期复用，换成验证码后**客户端不再生成、不持久化任何凭证**，只持久化服务端下发的令牌；会话稳定性改由服务端 `users` 表（邮箱唯一）承担。这正是 9.12 里"真实微信登录"将来若要做，也应当遵循的结构。

### 9.11 服务端成绩入库被外键拒绝（旧库迁移）

**问题。** 排行榜上线后，用"内置关"发起的对战成绩写不进 `solve_records`。

**根源。** 建表时 `solve_records.puzzle_id` 带了指向 `puzzles` 的外键，而内置关（正 id）的数据固化在客户端 `Levels.kt` 中、**不在服务端 `puzzles` 表里**（该表按约定只存负 id 的在线关），因此外键约束直接拒绝了这些合法的对局成绩。

**解决。** 去掉该外键（`puzzle_id` 保留为逻辑引用），并在 `init_db()` 里写一次性迁移：检测到旧表仍带该外键时重建表并复制数据。同时把这条约定写入注释——"外键不是越多越好，跨信任边界（客户端内置数据）的引用不该用数据库约束表达"。

**同类问题（登录方式改造时踩到）。** `users` 表新增 `email` 列后，若把 `CREATE UNIQUE INDEX ... ON users(email)` 写在建表脚本里，旧库启动时会因"列不存在"直接抛 `no such column: email` 而**整个服务起不来**。修正为先 `PRAGMA table_info` 探测、`ALTER TABLE` 补列、再建索引，并把迁移写成幂等（重复启动不报错），最后专门用"构造旧 schema → 启动 → 校验老账号数据仍在"的方式回归验证。

### 9.12 改进思路（对应实验加分项）

1. **鸿蒙端 / 小程序端**：逻辑层（`model`）为纯 Kotlin 零 Android 依赖，服务端与 HTTP / WS 协议无需任何改动，理论上只需重写界面层即可产出第二端——这也是本学期实验"同时实现两个平台"要求的后续工作；

2. **真微信登录（若将来具备资质）**：需要"微信开放平台已认证主体的移动应用 + 应用过审 + 应用签名登记"，客户端集成 OpenSDK（`SendAuth.Req` + 必须的 `WXEntryActivity` + Manifest `<queries>`），服务端改调 `sns/oauth2/access_token` 并在 `users` 表增加 `unionid` 列以支持多端统一账号；**客户端绝不能复用一次性 code**（见 9.10）。当前的账号体系已经预留了这条路：令牌 / 会话 / 进度分片都与登录方式解耦，替换的只有"身份凭证从哪来"这一段；

3. **成绩防作弊**：单人成绩目前仍是客户端自报时长（对战成绩已由服务端计时）。可让服务端下发题目时附带签名与下发时刻，提交时校验"时长 ≥ 服务器记录的题目持有时间"；

4. **更多关卡主题与难度曲线**：随机像素画生成器目前是"矩形 / 椭圆 / 三角形叠加"，可扩展为手绘图案库 + 元胞自动机，配合唯一解闸门批量产出新题；

5. **本地离线排行与训练模式**：用 Room 记录每关历史用时曲线，做个人最好成绩趋势与"重刷最速"玩法；

## 十．总结

本项目完成了一款规则严谨、交互流畅、界面完整的 Android 原生 Fill-a-Pix 像素填空解谜游戏，主要收获与结论如下：

**1、以"唯一解"为核心的质量观贯穿全程。** 从需求阶段就确立"每关谜面必须算法证明唯一解"的硬约束，形成了"提示推导 → 贪心去提示 → 求解器校验 → 单元测试把关"的闭环：Kotlin 单元测试在每次构建时重新证明 10 关唯一解，Python 脚本从另一侧独立回归。这直接回应了康思游戏评分体系中"规则理解是否到位""每道游戏是否确定唯一解"两个关键点，也让后续改关（如修正笑脸、月亮）有安全网可依赖。

**2、算法能力覆盖"生成"与"求解"两端。** 自研约束传播 + 回溯求解器既用于谜面质量闸门，也具备对任意谜面解题的能力；提示推导与稀疏化生成让新关卡制作成本降到"画一幅图 + 跑一次脚本"，具备游戏自动生成管线（评分点 3）。

**3、工程分层带来真实的开发效率。** 逻辑层零 Android 依赖的设计使 59 项客户端测试毫秒级运行；UI 层的问题（滚轮误触、结算溢出、棋盘过小）与逻辑层的问题（图案缺陷、提示失效）可以独立定位、独立修复、独立验证。项目中出现的多次返工（三支笔 → 智能双向笔、滚轮缩放加入又移除、浅色 → 恒定深色）都是在真实使用反馈下的小步迭代，体现了"可用性优先于炫技"的产品判断。

**4、交互细节决定解谜手感。** 笔划机制（一笔一撤销、可取消）、起笔定向智能笔、双指落下自动回滚误涂、滚轮/右键完全净化、错误检查"默认不打扰"、求解器反哺的"提示下一步"——这些细节共同构成了"用笔画画"而非"点格子填表"的核心体验，是本作品区别于普通填表实现的主要特色（评分点 4）。

**5、联网功能把单机解谜扩展成了多人对抗。** 游戏从网络获取（题库 + 每日一题，服务端即时生成并校验唯一解）、排行榜（每题每人最优成绩）、网络对战（WebSocket 房间、服务器权威计时与判定）与蓝牙对战（RFCOMM 直连，双端对称仲裁）四项加分项全部落地；其中"服务器不接受客户端自报成绩"与"在线题必经唯一解闸门"两条约束，让联网能力没有以牺牲公平性和谜题质量为代价。

**6、登录做成了真的。** 最初为满足"小程序登录"要求做的"微信式一键登录"经调研确认无法以我们可获得的资质真实接入，且原实现里服务端从未真正验证过任何凭证。最终改为**邮箱 + 6 位验证码**登录：SMTP 真实投递、服务端校验哈希 / 有效期 / 单次使用 / 频率限制后签发令牌，并保留控制台兜底通道以便离线演示。这次改造的取舍过程（9.10）与随之暴露的旧库迁移问题（9.11）是本项目在"工程诚实性"上最有价值的一课。

**7、不足与展望。** 单人成绩仍为客户端自报时长（对战已由服务端计时）；鸿蒙端与微信小程序端尚未实现（服务端与协议已为其预留，零改动即可复用）；关卡图案生成器目前限于几何图形叠加。后续将按"鸿蒙端 → 成绩防作弊 → 图案库扩充"的顺序继续迭代。

通过本项目的完整开发周期（需求 → 设计 → 编码 → 测试 → 文档），小组成员切实掌握了移动应用的分层架构设计、Compose 声明式 UI 与状态管理、Canvas 自绘与手势系统、网络编程（REST / WebSocket / 蓝牙）与服务端开发（FastAPI + SQLite）、轻量持久化与多线程，以及纯 JVM 单元测试与配套工具链建设等工程能力，达到了实验目的的各项要求。

## 十一. 鸿蒙(HarmonyOS)版

Android 与鸿蒙两端**共用同一个服务端与同一套协议**,鸿蒙端属于"客户端重写"——
服务端代码零改动,因此两端可以同房对战。

### 11.1 技术与结构

| 维度 | Android 版 | 鸿蒙版 |
|---|---|---|
| 语言 / UI | Kotlin 2.2 + Jetpack Compose | ArkTS + ArkUI 声明式(HarmonyOS 6.1.1 / API 24) |
| 目录 | `app/src/main/java/.../` | `harmony/ets/`(**同名镜像**:model/data/api/auth/battle/service/ui) |
| 网络 | Retrofit + OkHttp | `@kit.NetworkKit`(http / webSocket) |
| 存储 | SharedPreferences | `@kit.ArkData` preferences(**键名与安卓端相同**) |
| 音效 / BGM | SoundPool / MediaPlayer | `media.SoundPool` / `media.AVPlayer` |
| 单测 | JUnit(59 项) | `@ohos/hypium`(30 项) |

### 11.2 三个关键工程决策

1. **关卡数据用脚本生成,不手抄。** `tools/gen_harmony_levels.py` 从 `Levels.kt`/`SparseClues.kt`
   生成 ArkTS 关卡数据,生成时逐关自检:图案与 `Levels.kt` 逐行一致、提示集唯一解、唯一解 = 图案答案。
   这直接消除了"双源漂移"(安卓端曾经踩过的坑,见 9.3)。
2. **ArkTS 源码托管在本仓库 `harmony/`**,DevEco 工程只是构建工作区,用
   `tools/sync_harmony.py` 一键同步 —— 移植成果可评审、可 diff、可回溯。
3. **验证方式:单测即编译闸门。** ArkTS 只编译"被引用到"的文件,因此每写一层逻辑,
   都用 hypium 单测 import 它,既跑用例又强制编译;UI 层则靠 `assembleHap` 全量编译把关。

### 11.3 功能一致性

两端功能对等,差异仅在平台能力:`蓝牙对战`在鸿蒙端**不实现**(HarmonyOS 的
SPP/RFCOMM 支持与机型强相关),鸿蒙只保留网络对战。其余(登录、内置关、题库、每日一题、
排行榜、网络对战、音效与 BGM、摇一摇重置、断网提示、设置项)与安卓端一一对应,
帧协议与 DTO 字段完全一致。

### 11.4 真机联调:三个典型问题的定位与修复

真机首轮测试暴露三个问题,均已修复并重新编译验证(详见 `鸿蒙版移植计划.md` 第 9 节):

| 问题 | 根因 | 修法 |
|---|---|---|
| 邮箱登录登不上 | ① 默认服务器地址沿用了安卓模拟器的宿主机别名 `10.0.2.2`(鸿蒙模拟器/真机都不认);② 服务端没走带 `smtp.env` 的启动脚本,邮件发不出去 | 默认地址改为开发机局域网 IPv4;登录页/设置页新增**「测试连接」**自检(请求服务端 `/` 并回报 SMTP 是否就绪);网络失败文案带上"正在连哪个地址" |
| 填涂背景不一致(棋盘四周多出一圈颜色) | 旧实现用 `min(宽向, 高向)` 定格子边长,画布比棋盘"胖"时四周留白 | 画布先铺页面同色;格子边长改 `max(宽向, 高向)` 让纸面铺满;进关自动按**整盘适配**定基准缩放;色值与安卓端逐个对齐 |
| 格子里的数字太小 | 字号系数只有 `0.44 × 格子边长`、下限 8px,大棋盘上约 5px | 字号系数提到 `0.52` + 下限 10px + 上限 22px;**进关自动适配放大**,大棋盘不必先捏合;数字按大小分色;新增双击放大/还原与「⤢ 整盘」按钮 |

> 这一轮也说明了"双端一致性"的另一层含义:**配色与视口语义要对齐**,只对齐数据与协议
> 并不足以让两端看起来是同一个游戏。

### 11.5 第二轮全面检查:13 条问题与 UI 冒烟测试

在两端功能都跑通之后,又做了一轮**全面检查**(方法:符号级机械比对 `tools/compare_platforms.py`
+ 逐层人工审读非 UI 逻辑 + 实跑两端单测与服务端冒烟),查出 13 条问题并**全部修复**。
其中两条是**两端共有**、演示时最容易翻车的:

| 问题 | 根因 | 修法 |
|---|---|---|
| **游客点两下被踢回登录页** | 游客没有令牌,而"任何 401 就全局登出"把"没令牌"当成了"令牌失效";对战/排行榜入口也没拦游客 | 只在**本来持有令牌**时才全局登出;入口拦游客并提示需登录 |
| **困难关点「提示」卡死界面数秒** | 求解器为证明唯一性要搜完整个解空间(28×28 实测数秒),且同步跑在 UI 线程 | 改"两级限时":300ms 只做约束传播 → 不够再 1500ms 完整求解 → 都超时给降级提示,**UI 最多阻塞 1.8s** |

其余修复:服务器地址归一化(修掉"测试连接通过、保存后全部联网失败")、WebSocket 帧解析加字段校验
(畸形帧忽略而不打断连接)、背景音乐冷启动忽略用户开关、断网红条被误清、关卡缓存并发丢更新、
音效与播放器的资源释放和失败重试、诊断日志按字节写入。

**并补上了 UI 导航冒烟测试(两端各 7 项)**:真机上踩过的"点「下一关」没反应""最后一关留死按钮"
根因都在**导航**而不是渲染,因此把导航抽成纯逻辑 `ui/ScreenStack`,断言"下一关必须换关(不能是同一关)、
最后一关返回空、关卡表不断链、模式跟着带过去"。这类问题从此不必再靠真机手点发现。

当前测试规模:**安卓 59 项**(8 个测试类)、**鸿蒙 30 项**(4 个测试类),两端全绿。
