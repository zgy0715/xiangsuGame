## 一、实验目的

本次综合设计以一个完整的、可交付的双端游戏为载体，训练从**需求分析 → 系统设计 → 编码实现 → 测试验证 → 部署运行**的完整工程闭环，具体目标有四条：

第一，掌握中小型项目的需求分析、系统设计、编码、测试与部署运行方法，具备解决复杂工程问题的能力。本项目的"复杂"体现在：同一套玩法要在 Android 与鸿蒙两个平台原生实现，还要与同一个服务端、同一套网络协议协同工作，任何一处协议或数据不一致都会导致双端无法对战。

第二，掌握综合运用移动开发知识点进行项目管理与软件开发的能力。项目实际用到了界面与布局、自定义绘制、控件使用、网络请求、WebSocket 长连接、数据库、数据持久化、多线程与异步、传感器、广播/系统事件监听、图像与音频等，覆盖课程考核点的绝大部分。

第三，掌握文献检索、系统建模与文档写作能力。项目涉及的 Fill-a-Pix 规则、唯一解判定、NTP 式时钟校准、HarmonyOS ArkTS 语言限制等均通过查阅官方文档与技术社区资料解决，并沉淀为项目文档。

第四，综合运用所学知识完成项目开发，做到"能跑、能演示、能讲清楚"。为此项目不仅实现了基本玩法，还实现了自动出题、排行榜与网络对战等加分功能。

## 三、选题

### 3.1 系统简介

本项目是一款**像素填空（Fill-a-Pix）逻辑解谜游戏**，玩法与康思谜题官网的同名游戏一致：棋盘上散布着数字提示，每个数字表示"以它为中心的 3×3 区域内需要涂黑的格子数量"，玩家依据这些线索推理出每一格的最终状态（涂黑 / 留白 / 未定），把所有涂黑格连起来，最终会显现出一幅像素画。

与"直接给答案让人涂色"的涂色游戏不同，像素填空的**每一个数字都是一条硬约束**，玩家必须靠逻辑推导而不是猜测来完成，因此它同时具备推理训练的严谨性与"揭晓图案"的惊喜感——这是它作为课程作品的核心吸引力。

本项目不是单机 Demo，而是一套完整系统：两端原生客户端 + 一个共用服务端。客户端负责交互与实时校验，服务端负责账号、出题、成绩与对战裁决。两端**共用同一个服务端与同一套协议**，因此可以同房对战。

![图 3.1　游戏主界面与解谜中的棋盘](docs/images/fig3-1-home-game.png)

### 3.2 为什么做这个游戏

选择像素填空而不是常见的"打砖块 / 2048"，主要基于三点考虑。

第一，**它能撑起真正的算法含量**。课程评分明确关注"能否算法解题""能否生成游戏""每题是否确定唯一解"，而像素填空天生适合：它的约束是局部且可判定的，可以用约束传播快速推导，用回溯搜索枚举解空间并判定唯一性；反过来，只要给定唯一解与稀疏提示，就能自动生成一道合格题目。这意味着项目可以自研一个真正的求解器与出题器，而不是把题目写死在资源文件里。

第二，**它能自然承载"网络 + 数据库 + 多线程 + 传感器"这些考核点**。因为每题唯一解、答案可机器校验，所以"同题竞速"这种对战玩法可以被服务器公平裁决；因为要记录每人每题最优成绩，所以需要数据库与排行榜；因为棋盘要流畅交互，所以需要自定义绘制与手势处理；再加上摇一摇重置、音效与背景音乐、断网提示，几乎把课程的考核点全覆盖了。

第三，**它适合作为"跨平台一致性"的工程训练**。同一款游戏用两套完全不同的原生技术栈实现，并且要求"功能、玩法、界面、数据、协议完全一致"，这迫使我们把架构分层做干净：把纯算法逻辑与平台 API 彻底分离，才能用一份设计指导两端实现。这一点最终成了本项目最有价值的部分（详见 5.1 与 7.5 节）。

### 3.3 系统概览

系统由三部分组成：**Android 客户端**、**鸿蒙客户端**、**Python 服务端（含 SQLite 数据库）**。

客户端的主要能力包括：邮箱验证码登录与游客离线模式；10 个内置关卡（顺序解锁）与进度记录；在线题库（按难度筛选、分页加载、自动生成）；每日一题（全服同题）；排行榜（按题目选择、单人榜与对战榜）；网络对战（建房/加房/选题/发车/实时进度/服务器判名次）；一键补齐额度（每日登录 +2）；提示下一步与参考答案；摇一摇重置棋盘；音效与背景音乐；断网提示条与离线缓存重玩。

服务端的主要能力包括：邮箱验证码的生成、发送与校验（含限流与防爆破）；账号与令牌管理；题目的自动生成与唯一解校验；题库与每日一题的提供；成绩落库与排行榜聚合；对战房间的建立、状态广播、计时与名次裁决。

## 四、需求分析

### 4.1 功能需求

**账号与登录。** 系统不设用户名密码，用户输入邮箱后，服务端生成 6 位验证码并尝试通过 SMTP 发信；用户填写验证码，服务端校验通过后签发 30 天有效的 Bearer 令牌。首次登录自动注册账号并引导设置昵称。为便于开发与现场演示，服务端支持"未配置 SMTP 时把验证码打印到控制台"，也支持通过演示开关让验证码直接显示在 App 内。

> **关于"要求小程序登录"的说明。** 课程原文要求"不需要用户名密码登录，要求小程序登录"，即希望避免自建密码体系。本项目最初实现的是微信登录，但微信开放平台的登录能力需要企业主体资质与审核，个人作品无法在课程周期内合规接入，因此**改为成本更低、体验等价且更符合教学演示场景的"邮箱 + 验证码"免密登录**：用户依然不需要记密码，服务端依然通过第三方通道（邮件）验证身份，而且完全自主可控、答辩现场可现场演示。这一取舍在"存在的问题"一节中也有说明。

**游客与离线。** 用户可不登录直接以游客身份进入，玩全部内置关卡，完全离线可用；在线功能（题库、每日一题、排行榜、对战）需要登录。这一设计保证了"断网或服务器不可达时作品依然可演示"。

**游戏玩法。** 支持两种画笔（涂黑笔、留白笔）、按住拖动连续涂一格宽的笔划（整笔作为一步撤销）、撤销/重做/重置、显式"检查错误"（平时不打扰，点击后精确标红）、提示下一步（用求解器推导确定格）、一键补齐（额度制）、查看参考答案、自由模式与限时挑战两种模式、通关揭晓与"下一关"。

**网络获取题目。** 在线题库按难度（简单/中等/困难）与随机尺寸（8～20 格）由服务端即时生成；每日一题按日历日确定性生成，保证全服同题；两种情况都必须在服务端通过唯一解校验后才下发。

**排行榜。** 每道题取每人最优成绩排名，展示"我的最佳"；对战成绩由服务器计时并单独成榜；用户可切换题目查看不同题目的榜单。

**对战。** 网络对战支持 2～4 人：房主创建房间得到 4 位房号，其他人凭房号加入；房主选一道题后发车，全员同题同时开跑；竞速过程中实时看到彼此进度；第一个完整还原图案者获胜，名次与用时由服务器权威判定；结束后可再来一局。Android 端另支持两台设备通过蓝牙直连对战，无需服务器。

**设置。** 服务器地址（含"测试连接"自检）、音效开关、背景音乐开关、摇一摇重置开关、演示模式全解锁、昵称修改、退出登录。

### 4.2 非功能需求

**性能。** 棋盘拖动连涂与双指缩放在 28×28 的大棋盘上无可感卡顿；提示求解必须有时间上限（不能出现"点一下卡住几秒"）；服务端启动时后台预热题库，首屏不卡在题目生成上。

**可靠性。** 服务端不可达时客户端不能崩、不能白屏，应给出可操作的提示并保留离线可玩路径；令牌失效时自动回到登录页；对战中途断线应能重连且不丢席位与进度。

**安全性。** 验证码只存哈希、10 分钟过期、单次使用、错误次数上限；同一邮箱有重发间隔与每小时/每天发送上限；同一 IP 有发送频率上限；令牌可被服务端注销；邮箱授权码等密钥只存在于本机环境变量，绝不入库。

**一致性与可维护性。** 两端的玩法、数据、协议、配色必须一致；纯算法逻辑必须与平台 API 解耦，以便单测覆盖与将来复用到小程序端。

**可测试性。** 核心算法、状态机、协议编解码、导航逻辑都要有自动化测试；服务端要有可重复运行的冒烟测试。

### 4.3 用例分析

系统的主要参与者有两类：**注册玩家**与**游客**，另有**服务端**作为外部参与者提供系统级服务。

注册玩家的主流程是：邮箱验证码登录（包含"获取验证码""校验验证码""校验令牌"三个子用例）→ 进入首页 → 选择模式与关卡 → 涂格推理 → 撤销/重做/检查/提示/补齐/看答案 → 通关结算 → 解锁下一关。在线侧另有四条扩展用例：玩每日一题、浏览在线题库、查看排行榜、创建或加入对战房间。

游客的流程是：跳过登录直接进入首页，仅可玩内置关卡（离线用例），随时可"切换账号"回到登录用例。

服务端作为系统参与者提供五个服务：发送验证码邮件、校验验证码并签发令牌、即时生成并校验关卡唯一解、裁决对战名次与计时、聚合排行榜。

其中"涂格推理"是最核心的用例，其主成功场景为：玩家选中涂黑笔 → 在空白格按下（涂黑）→ 拖动经过多个格子（连续涂黑）→ 抬起（整条笔划提交为一步）。扩展场景包括：按下时第二根手指落下（取消本条笔划，转为缩放）、落在已涂黑的格子上（本笔自动变为清除方向）、棋盘处于通关或超时状态（冻结交互，仅可查看）。

### 4.4 运行环境与约束

Android 端最低支持 Android 7.0（API 24），编译与目标版本为 API 36，使用 Kotlin 2.2 与 Jetpack Compose。鸿蒙端目标为 HarmonyOS 6.1.1（API 24），使用 ArkTS 与 ArkUI 声明式开发。服务端运行于 Python 3.13，依赖 FastAPI 与 Uvicorn，数据库使用 Python 标准库自带的 SQLite，不引入额外依赖。

一项重要约束是：**鸿蒙端不实现蓝牙对战**。HarmonyOS 对经典蓝牙 SPP/RFCOMM 的支持与机型、系统版本强相关，在课程周期内无法保证稳定演示；因此鸿蒙端只保留网络对战，并在对战大厅界面明确说明原因。由于两端共用同一套网络协议，这一取舍不影响"双端同房对战"这一核心验收点。

分层的关键决策是：**把"游戏怎么玩"与"用什么画、怎么联网"彻底分开**。逻辑层（`model/`）不引用任何平台 API，因此它可以被单元测试直接覆盖（毫秒级运行），也可以在两个平台上按同一份设计逐行实现，还能在未来复用到小程序端。这条决策在实施中被反复验证是值得的：当两端出现行为不一致时，我们能立刻判断是"逻辑分叉"还是"界面差异"。

### 5.2 模块划分

客户端按职责划分为五个包：`model`（核心算法与数据模型）、`data`（持久化与业务仓库）、`auth`（登录与会话）、`battle`（对战协议与状态机）、`ui`（界面与控件），另有两个横切模块 `service`（音效/背景音乐/网络监听）与 `sensor`（摇一摇）。

服务端按路由划分模块：`auth.py` 负责验证码与令牌，`puzzles.py` 负责题库与每日一题，`leaderboard.py` 负责成绩与榜单，`rooms.py` 负责房间与对战（含 WebSocket），`content.py` 与 `generator.py` 负责题目生成，`puzzle_engine.py` 提供共享的求解与唯一解校验引擎，`mailer.py` 负责发信。

值得一提的是，**服务端与工具链共用同一份 Python 谜题引擎**：内置关卡的提示生成脚本、唯一解校验脚本、以及线上出题流程都调用 `puzzle_engine.py`。这样"判定标准"只有一份实现，避免了两端各写一套求解器导致的判定漂移。

### 5.3 数据库设计

**（1）概念设计。** 系统涉及五个核心实体。**用户**（邮箱唯一）是账号主体；**验证码**依附于邮箱，记录哈希、有效期、是否已用与失败次数；**题目**记录题面（行列数、提示矩阵、答案矩阵）与来源（题库/每日一题）；**每日一题**记录日期到题目的映射，保证全服同题；**成绩记录**记录某用户在某题上的用时、来源（单人/对战）与名次。用户与成绩是一对多，题目与成绩是一对多，用户与验证码通过邮箱弱关联（未注册邮箱也能发码）。

**（2）逻辑设计。** 六张表的结构如下。

**表 5-1　数据库逻辑结构**

| 表名 | 关键字段 | 说明 |
|---|---|---|
| `users` | user_id(PK) · email(UNIQUE) · nickname · created_at | 账号主体，邮箱唯一 |
| `tokens` | token(PK) · user_id(FK) · created_at · expires_at | 登录令牌，30 天有效 |
| `puzzles` | puzzle_id(PK) · source · difficulty · rows · cols · clue_grid · answer_grid | 在线题目及来源 |
| `daily` | day(PK) · puzzle_id | 每日一题：日期 → 题目 |
| `solve_records` | record_id(PK) · puzzle_id · user_id · duration_ms · source · created_at | 成绩，按题目+用户取最优 |
| `email_otps` | otp_id(PK) · email · code_hash · expires_at · used · attempts | 验证码，只存哈希 |

设计上的三个要点：**其一**，验证码只保存 sha256 哈希，即使数据库泄露也无法直接得到可用验证码；**其二**，成绩表用 `source` 字段区分单人成绩与对战成绩，因为对战成绩由服务器计时，可信度与单人自报不同，展示时必须分榜；**其三**，题目表保存的是"提示矩阵 + 答案矩阵"，而不是一个整数 ID —— 因为题目是服务端即时生成的，必须把题面本身落库，否则对战中无法把同一道题下发给多个玩家。

**（3）物理设计。** 数据库采用 SQLite 单文件存储（`server/xiangsu.db`），开启 WAL 模式以提升并发读写能力。索引方面：`users.email` 建唯一索引（登录查询与防重复注册）、`solve_records(puzzle_id)` 与 `solve_records(user_id)` 建普通索引（排行榜聚合与"我玩过的题"查询）、`email_otps(email)` 建索引（取最新验证码与限流统计）、`tokens.expires_at` 用于清理过期令牌。排行榜查询用窗口函数 `RANK() OVER (ORDER BY best ASC)` 一次算出名次，避免在应用层做 N 次查询。所有写操作走统一的 `session()` 上下文管理器，保证提交与关闭成对出现。

### 5.4 关键设计决策

**决策一：关卡数据用脚本生成，不手抄。** 内置关卡的图案与提示在两端的代码里各有一份，手抄必然漂移。项目编写了生成脚本，从 Android 端的关卡定义直接生成鸿蒙端的 ArkTS 数据文件，生成时逐关自检"图案逐行一致、提示集能推出唯一解、唯一解等于图案答案"，三重校验通过才写出文件。

**决策二：题目唯一解是硬闸门。** 出题流程的最后一步必须是唯一解校验：如果一道题的提示不足以唯一确定答案，玩家就可能"看着线索也推不出来"，这是此类游戏体验崩坏的根源。因此服务端生成的每一道题（题库、每日一题、对战选题）都要过这道闸门，不通过就重新生成。

**决策三：对战名次与用时由服务器裁决。** 客户端只能"自报进度"，用来做实时展示；决定名次与成绩的是服务器收到完成帧的先后顺序，用时也由服务器计时。这样既保证了公平性，也让对战成绩可以进排行榜。

## 六、详细设计

### 6.1 玩法规则的形式化

把规则写成可判定的形式，是后面所有算法的基础。棋盘有 `rows × cols` 个格子，每格状态取三值：**未定（0）、涂黑（1）、标记留白（2）**；每个有提示的格子 `(r,c)` 带一个数字 `clue[r][c]`，表示以它为中心的 3×3 窗口内**必须恰好有这么多格被涂黑**。

在此基础上定义三个判定函数，它们是整个项目的"事实标准"：

**已满足提示**：某提示窗口内已无未定格，且涂黑格数恰好等于提示值 → 该数字达标（界面把数字变绿，作为正向反馈）。

**错误格**：某格已被玩家确定（涂黑或标记留白），但"它是否涂黑"与答案不符 → 错误格（仅在玩家主动点击"检查"后标红，平时不打扰）。

**通关**：所有格子的"是否涂黑"都与答案一致（标记留白与未定都算作未涂黑）。注意通关判定只用涂黑与答案比对，因此玩家标不标留白不影响通关，只影响自己的推理习惯。

### 6.2 求解器：约束传播 + 回溯

求解器要回答两个问题：**这道题有几个解**，以及**当前盘面下哪一格是逻辑上可确定的**。

算法分两步交替执行。**第一步是约束传播**：对每个提示窗口，统计其中已确定的涂黑数与未定格数，若"已涂黑数等于提示值"则把窗口内所有未定格确定为留白；若"已涂黑数 + 未定格数等于提示值"则把未定格全部确定为涂黑。这一步不猜，纯推导，代价极低，而且能解决大部分格子。**第二步是分支**：若仍有未定格，选一个格子先试涂黑再试留白，递归进入下一层，回溯时还原现场。

搜索带三个必要的工程约束。**解数上限**：校验唯一解时只需求到两个解就可以提前停止（说明不唯一），这能省掉大量无谓搜索。**时间上限**：搜索带截止时刻，超时提前中止，并通过"是否超时"标志告诉调用方"这个结果不可信，不能当作无解或唯一解的判定依据"。**初始约束**：可以把玩家当前盘面作为硬约束带入求解，这样求解器就在"保留玩家已做的推理"前提下继续推。

「提示下一步」正是建立在第三个约束上：把玩家盘面作为初始约束求解，优先提示"根节点约束传播就能确定的格子"（也就是纯逻辑一步可推的），若没有则取唯一解下第一个未定格（它的状态由唯一解锁定，同样可推导）。

需要特别说明一处**性能设计**。求解器为了确认"这一步必须这么走"，原则上要搜到证明没有第二个解才返回；在 28×28 的大棋盘上这是重负载（实测可达数秒）。而"提示"是用户点击触发的同步操作，一旦超过一帧就会让界面失去响应。因此最终实现改成了**两级限时**：先用很短预算（300 毫秒）只做约束传播，绝大多数盘面在这一步就能给出提示；若不够，再用较长但仍有上限的预算（1500 毫秒）完整求解；两者都超时就给一句降级提示（"这一步暂时推不出来，先随手确定一格再试"）。这样无论盘面多难，界面最多阻塞 1.8 秒，绝不会"点一下卡死"。

### 6.3 出题器：从答案反推提示

自动出题走的是"先画图、再去提示、再验解"的路线。

**第一步生成图案**：随机叠加矩形、椭圆、三角形等几何图元形成一幅像素画，随机过程用固定种子驱动，保证同一种子可复现同一幅图。

**第二步稀疏化提示**：如果每个格子都保留提示，题目就毫无难度。因此从"全提示"开始，贪心地尝试去掉提示，每去掉一个就重新校验解是否仍然唯一，直到再删任何一个都会破坏唯一性为止。这样得到的提示集是"刚好够用"的。

**第三步唯一解闸门**：用求解器枚举解空间，要求"有且只有一个解，且该解等于原始图案"，否则整题作废重新生成。

难度分级按尺寸与提示密度控制：简单档尺寸小、提示密，困难档尺寸大、提示稀。每日一题则把日期当作随机种子，从而保证同一天所有用户拿到完全相同的题目。

### 6.4 棋盘交互：笔划语义与撤销栈

填涂手感的细节决定了这款游戏"好不好用"，因此棋盘交互做了专门设计。

**双向智能笔与整笔语义**：玩家不需要在"涂黑"和"擦除"之间反复切换工具。按下时若落点是未定或留白格，本笔方向为"涂黑"；若落在已涂黑的格子上，本笔方向自动变为"清除"。方向一旦由起笔那格确定，整条笔划内保持一致。整条笔划在抬起时才提交，作为**一步**进入撤销栈——这样"拖一条长线涂错"只需要撤销一次，而不是撤销几十次。

**双指与单指的职责分离**：单指用于涂色，双指用于缩放与平移。实现上有一个关键细节：第二根手指落下的瞬间要**取消当前笔划**，否则玩家想缩放时手指的移动会被误当成涂色，导致"一缩放就涂花一片"。

**检查结果的快照语义**：玩家点击"检查"后标出的错误格，会在下一次落笔时清除，而不是实时跟随。这符合"检查是一次快照"的心理模型，也避免了红框在拖动过程中不停闪烁。

**异常状态的兜底**：游戏页还做了两处防呆。一是"只差几格"提示：由于涂黑笔在已涂黑格上是擦除语义，玩家"想再确认一下"的点击有可能把刚涂好的格子擦掉，导致盘面看着全对其实少一格；此时界面会明确提示"还差 N 格没涂"或"多涂了 N 格"，并且可以点击该提示直接标出问题格。二是通关看门狗：每秒独立兜底判定一次通关，判定只依赖棋盘快照这个唯一事实来源，即使触摸事件偶发丢失也能正确结算。

### 6.5 对战协议与服务器权威计时

对战设计上把"网络传输"与"竞速状态"分开：`BattleTransport` 定义传输抽象（连接、发送、关闭与回调），`NetworkBattleTransport` 是它的 WebSocket 实现，`BattleSession` 是与传输无关的状态机。这样同一套状态机既可用于网络对战，也可用于蓝牙对战（Android 端两种传输共用同一状态机）。

协议采用 JSON 文本帧，分为上行与下行两类。上行包括：认证（首帧带上令牌）、准备、房主选题、发车、进度上报、完成上报、请求重赛、校时请求。下行包括：房间状态、玩家加入/离开、开跑（含题目与服务器开跑时刻）、他人进度、他人完成、结算结果、错误提示、校时回包。每个帧带一个类型字段，接收方按类型分发；**对帧内容必须做字段校验**，缺字段或类型不符时忽略该帧继续运行，绝不能让一个畸形帧把连接打断。

关于计时的设计值得单独说明。若让各客户端用自己的本地时钟计时，则"谁先完成"会因设备时钟漂移而不可比。因此本项目采用**服务器权威计时 + NTP 式校时**：开跑时刻由服务器下发（服务器时钟），客户端收到后先回一个校时请求，用往返时延的一半估算自己与服务器的时钟偏移，之后展示的用时就用"服务器时钟下的当前时刻减去服务器开跑时刻"计算。名次则由服务器按接收完成帧的先后顺序判定。这样玩家看到的用时、结算显示的用时、以及写进排行榜的用时，三者口径一致。

房间的生命周期也做了容错设计：玩家掉线后席位与进度会被保留一段时间（宽限期），期间重连即可回到原房继续；若房主掉线且超过宽限期仍未回来，服务器会回收房间并通知剩余玩家，避免出现"卡在房间里无法继续"的死局。

![图 6.1　对战房间与竞速界面](docs/images/fig6-1-battle.png)

### 6.6 蓝牙对战（Android 端）

Android 端另实现了两台设备直连对战，无需服务器与网络。两端通过蓝牙 RFCOMM 建立串口式连接，一方作为发起方、另一方作为接受方，连接建立后复用与网络对战相同的帧协议与状态机。

蓝牙场景没有可信的第三方裁判，因此采用**双端对称仲裁**：双方各自在本地校验自己的棋盘，完成后把"涂黑掩码"与用时发给对端，双方各自独立计算名次。为避免"双方都以为自己赢"的情况，比对时用掩码与完成时间的确定性组合作为排序依据，并在界面上明确展示对端的完成情况。此外，蓝牙链路的连接失败（配对失败、设备不支持、权限被拒等）都给出了可读的中文提示，而不是让界面停在"连接中"。

## 七、系统实现

### 7.1 开发环境与技术选型

Android 端使用 Kotlin 2.2 与 Jetpack Compose 声明式 UI，网络使用 Retrofit + OkHttp + kotlinx-serialization，持久化使用 SharedPreferences，音效使用 SoundPool、背景音乐使用 MediaPlayer，构建使用 Gradle（AGP 9.2.1）。

鸿蒙端使用 ArkTS 与 ArkUI（HarmonyOS 6.1.1 / API 24），网络使用 `@kit.NetworkKit`（HTTP 与 WebSocket），持久化使用 `@kit.ArkData` 的 preferences，音效使用 `media.SoundPool`、背景音乐使用 `media.AVPlayer`，传感器使用 `@kit.SensorServiceKit`，构建使用 DevEco Studio 的 hvigor 工具链。

服务端使用 Python 3.13 + FastAPI + Uvicorn + SQLite（标准库 `sqlite3`），发信使用标准库 `smtplib`，不引入额外第三方依赖。

### 7.2 服务端实现

**认证流程。** 发送验证码时，服务端生成 6 位数字码，入库时只保存 `sha256(邮箱 + 码)` 的哈希，并通过 SMTP 发送邮件；同时记录发送时间用于限流。校验时先做邮箱维度的失败节流（短时间内失败过多直接拒绝），再依次检查"是否有码、是否已用、失败次数是否超限、是否过期"，最后比对哈希，成功后立刻把该码标记为已使用。整套流程保证了验证码**一次性**、**有时效**、**不可枚举**。

**出题与每日一题。** 题库接口按难度返回随机尺寸的题目，命中"该难度至少要有 N 道保底题"的逻辑，避免演示时出现空列表；每日一题用日期作为随机种子，先查库，未命中再生成并落库，生成时通过唯一解闸门。

**成绩与排行榜。** 提交成绩时只接受单人来源（对战成绩由服务端在对局结束时自己写入，防止客户端伪造）；同一用户同一题只保留最优成绩。查询榜单时用窗口函数一次性算出名次，并额外返回"我的最佳"，让用户即使不在前 N 名也能看到自己的位置。

**房间对战。** 房间状态全部在内存中维护：创建房间生成 4 位房号，加入时校验房间是否存在、是否还在等待阶段、席位是否已满；房主选题后可发车，服务器把题目与开跑时刻广播给所有玩家；竞速过程中转发彼此的进度；收到完成帧时按接收顺序记名次并校验答案；全员完成后生成结算并写入成绩表。断线时保留席位，超过宽限期则清理。

### 7.3 Android 端实现

**界面结构。** App 采用单一 Activity + 手写页面栈的路由方式：根组件维护一个页面数组，页面之间通过压栈/出栈切换。外层负责全局关注点：启动时固定停在登录页（即使本地有续登会话，也要用户点"继续"才进入）、会话失效时自动重置回登录页、断网时顶部显示提示条。这种做法比引入导航框架更轻，也让"页面栈"这一数据结构可以被单元测试直接覆盖（见 7.6 节）。

**棋盘绘制。** 棋盘使用 Compose 的 Canvas 一次性绘制整盘：先画纸面底色，再逐格画状态底色、提示数字、错误标记与边框，最后套一层"装裱外框"。提示数字按数值大小分色（0 灰、小数字蓝、中等数字青、大数字紫、更大数字红），已满足的提示变绿，涂黑格上的数字变白——这些颜色规则既提升了可读性，也让玩家能一眼看出"哪些线索已经被我满足了"。

**手势与缩放。** 单指拖动负责涂色：实现上不是简单取"当前触点所在的格"，而是对相邻两个采样点之间做**插值**（按约半格步长细分），否则快速拖动会跳过中间的格子，出现断断续续的涂色。双指负责缩放与平移，并且第二指落下时会取消当前笔划。

**系统特性集成。** 摇一摇重置使用加速度传感器（带阈值与防抖，并且受设置开关控制）；断网提示使用网络状态监听；音效与背景音乐各自受设置开关控制，切后台自动暂停。

### 7.4 鸿蒙端实现

鸿蒙端的目标是**功能对等**，因此目录结构与 Android 端保持同名镜像（`model` / `data` / `auth` / `battle` / `service` / `sensor` / `ui`），文件职责一一对应，便于对照维护。

实现过程中遇到并解决了若干 ArkTS/ArkUI 特性带来的具体问题，这些是鸿蒙端最值得记录的经验：

**其一，ArkTS 只编译"被引用到"的文件。** 这意味着"编译通过"并不代表新写的库被编译过——因为没被任何页面引用到的文件根本不会进入编译。为此项目建立的规矩是：**每写一层逻辑，就写一个单元测试去 import 它**，既跑用例又强制编译。这一条后来成为鸿蒙端质量的主要保障。

**其二，ArkUI 会复用组件实例。** 在同一个渲染分支里只更换数据时，ArkUI 不会重建组件、也不会重跑 `aboutToAppear`。这一点直接导致过一个真实 Bug："点击下一关没反应"——原因是切关时用了"替换栈顶"的写法，栈长度没变，于是游戏页组件被复用，棋盘仍指向上一关的数据，看起来就像按钮失效。最终修法是**双保险**：切关改为"压栈"（栈长度变化会强制重建组件），同时给游戏页加一个关卡标识，并监听它的变化来重建棋盘与计时。

**其三，`enabled(false)` 是完全静默的。** 被禁用的按钮不响应点击、没有视觉反馈也没有提示，用户会直接认为"这个按钮坏了"。项目因此定下一条 UI 规范：**除非禁用理由对用户可见（如倒计时、加载中），否则不用 `enabled` 关按钮，而是让按钮可点、并在无效时给出具体原因**（例如"没有可撤销的操作""至少要 2 人在线才能发车"）。同时写了一个只读审计脚本扫描全仓按钮写法，把这类问题在提交前找出来。

**其四，性能与绘制的坑。** 棋盘每涂一格都需要重绘，如果每帧都逐格绘制文字，在网格密集时明显卡顿。最终实现把"纸面 + 网格 + 数字"这些**不变的内容预渲染成一张位图缓存**，每帧只需贴一次图再叠加有状态的格子；网格线也从"逐格描边"改成"每行/每列各一条线"。这一改动让 28×28 棋盘的交互明显流畅。

**其五，跨平台 API 的差异要按语义对齐而不是照抄。** 例如屏幕缩放、字号、内边距在两个平台上的默认行为不同，照抄数值反而会得到不同观感；又如"适配整盘"在两端的实现方式完全不同（一端靠布局约束，一端靠绘制变换）。项目的做法是：**先确定"用户看到什么"这个语义，再各用本平台最自然的方式实现**，最后用同一组参数（如"1 倍视图等于整盘适配""字号为格边长的 0.6 倍"）保证观感一致。

### 7.5 两端一致性是怎么保证的

"双端一致"如果只靠人工比对，几乎必然漂移。项目为此建立了三道机制。

**第一道是数据层的一次性生成。** 内置关卡的图案与提示只维护一份（Android 端），鸿蒙端的数据文件由脚本生成，生成时做三重校验（图案逐行一致、提示集唯一解、唯一解等于答案）。因此数据层面不存在"两边不一致"的可能。

**第二道是协议的字段级对齐。** 两端的请求/响应结构与帧字段保持一致，服务端不区分调用方平台。为验证这一点，服务端的冒烟测试里包含一个"裸 WebSocket 客户端"，它不依赖任何客户端代码、直接用 JSON 帧与服务端交互完成一局对战——这从外部证明了协议是平台中立的。

**第三道是可见的一致性审计。** 项目编写了一个只读审计脚本，按文件配对抽取两端的函数名、常量名与属性名做差集，快速筛出"鸿蒙端疑似少实现了什么"，再由人工确认。这套方法在一次全面检查中筛出了 50 多处差异（含 5 个严重隐患），并全部修复。它的价值在于把"一致性"从主观印象变成了可执行、可复现的检查。

### 7.6 补充：把"导航"抽出来做测试

项目后期发现，真机上暴露的界面问题几乎都不是渲染问题，而是**导航问题**（点下一关没反应、最后一关留着一个点了没反应的按钮）。于是把页面栈的导航计算抽成独立的纯逻辑模块（两端的 `ScreenStack`），界面只负责渲染与转发。这样导航就能被单元测试覆盖，断言包括：下一关必须给出**另一关**（不能是同一关——这正是"看着没反应"的本质）、最后一关返回空（界面据此隐藏按钮）、关卡表不断链、模式要跟着带到下一关。

两端的单测规模因此变为：Android 59 项、鸿蒙 30 项，全部通过。

### 8.4 功能与真机测试

功能测试在模拟器与真机上进行，覆盖的主要场景与其结论如下。

**登录链路**：正常发码与登录成功、验证码错误提示、重复使用旧码的提示、服务器地址错误时的可读报错、游客进入与后续转正。测试中发现"鸿蒙端登不上"的问题，最终定位为默认服务器地址误用了仅适用于 Android 模拟器的特殊地址，以及服务端未走加载发信配置的启动脚本（详见 9.1）。

**游戏交互**：单指连涂、双指缩放与平移、撤销/重做/重置、检查错误与清除、提示下一步、一键补齐、参考答案、限时模式倒计时、通关揭晓与下一关。测试中修掉了"通关后点下一关没反应""按钮点了没反应""棋盘数字太小""大棋盘超出边界"等问题（详见 9.2）。

**网络功能**：题库筛选与分页、每日一题、排行榜切换题目与榜别、建房加房、发车、竞速实时进度、结算与重赛、断线重连。测试中修掉了"对战里弹出单人通关遮罩导致被迫退房""看不到对手进度"等问题。

**离线与容错**：断网时给出提示条且内置关可玩、服务端不可达时的错误文案可操作、令牌失效自动回登录页。

**传感器与多媒体**：摇一摇重置、音效与背景音乐的开关与前后台行为。

### 8.5 性能测试

**求解性能**：10 个内置关卡的唯一解校验总耗时在毫秒级；最大关卡（28×28）在"从空盘推导提示"这一最重场景下，改造后由"可能数秒无响应"变为**最多 1.8 秒**且有降级提示。

## 九、遇到的问题、解决办法或改进思路

本节记录开发过程中真正卡住过的问题。它们大多不是"功能没写"，而是"平台特性与预期不符"，因此对后续开发很有参考价值。

**9.1 鸿蒙端邮箱登录不上。** 现象是输入邮箱后拿不到验证码。排查后发现两个叠加原因：一是鸿蒙端的默认服务器地址沿用了 `10.0.2.2`，而这个地址是 **Android 模拟器**访问宿主机的特殊别名，鸿蒙模拟器与真机都不认（`localhost` 又指向模拟器自身），必须填写开发电脑在局域网中的真实 IP；二是服务端当时是直接启动的，没有加载发信配置文件，于是"邮件根本没发出去"。解决办法：把默认地址改为开发机局域网 IP，并在登录页与设置页增加「测试连接」按钮——它会请求服务端根路径，直接告诉用户"地址对不对、邮件发送是否已配置"；同时在网络错误文案里明确写出"正在连接哪个地址"，把排查路径交给用户。

**9.2 棋盘相关的四个体验问题。** ①**填涂背景不一致**：棋盘格子外面出现了另一种底色，看起来像没铺满；根因是格子尺寸取"宽向与高向中较小者"，所以画布比棋盘"胖"时四周留白。②**大棋盘超出边界**：为了追求"铺满"，一度改成取较大者，结果关卡变大后棋盘内容溢出可视区域。这两个问题的正解是回到"**整盘适配**"——始终保证整个棋盘完整可见，想看清细节靠放大，而不是靠默认铺满。③**格子里的数字太小**：字号原来只有格边长的 0.44 倍且下限很低，大棋盘上不足 5 像素；调整为格边长的 0.6 倍并设下限，同时让用户一进关就看到"整盘适配"的合适倍率。④**画布四周的"白边"**：根因是画布擦除后露出容器底色，改为先把整张画布铺成页面同色即可。

**9.3 "点下一关没反应"。** 这是最有代表性的一次排查。最初以为是按钮的点击事件没接上，加了日志后发现点击其实执行了、页面栈也确实换了新关卡——问题在于**界面组件没有被重建**：ArkUI 在同一个渲染分支里更换数据时会复用组件实例，于是游戏页仍持有上一关的棋盘数据，"新关卡"看不见。修复用了双保险（改为压栈触发重建 + 监听关卡标识变化重建棋盘），并把导航逻辑抽出来加了测试，让这类问题以后能被自动发现而不是靠手点。

**9.4 "按钮点了没反应"。** 排查时写了一个只读脚本扫描全仓按钮写法，发现真正的元凶是**被 `enabled(false)` 静默禁用的按钮**：撤销栈为空、补齐额度用尽、房号不足四位、人数不足两人等情况下，按钮既不可点也无任何提示。修复方式是定下 UI 规范并用可点 + 具体原因提示替代静默禁用，同时把游戏页一行挤六个按钮的布局拆成两行，改善热区与可读性。

**9.5 困难关点提示会卡住。** 求解器为证明唯一性需要搜索整个解空间，而这个调用跑在界面线程上。改进思路有两个方向：一是**限时**（已采用），二是**异步**（把求解放到工作线程，界面显示加载态）。本项目选择了限时 + 降级提示，理由是改动小、收益确定；异步方案列入后续优化。

**9.6 鸿蒙端编译通过但功能没生效。** 起因是 ArkTS 只编译"从入口可达"的文件：新写的库如果没有任何页面或测试引用它，就不会进入编译产物，于是"编译成功"其实什么也没验证。这直接导致过"功能写了但没接线"的问题（例如摇一摇的检测类写好了却没有被任何页面使用）。解决办法是立规矩：**每写一层逻辑就配一个单测去引用它**，并在文档里明确"编译通过不等于验证过"。

**9.7 环境与工具链的"非功能性"故障。** 这类问题很耗时间但很典型：构建工具的守护进程崩溃后会导致后续每次构建都失败，需要绕开守护进程；Windows PowerShell 5.1 会按系统编码读取无 BOM 的 UTF-8 脚本，中文与特殊符号会直接造成语法错误；批处理脚本里的暂停命令在非交互环境下会永久挂住，看起来像"编译卡死"；签名所需的证书链格式、文件扩展名、参数都有严格要求。这些问题的解决过程被记录进了项目文档与一键脚本，使后续每次构建都能稳定复现。

**改进思路。** 短期内计划补三件事：把对战的服务器权威计时完整接到竞速界面的用时显示上；补齐宽屏/平板的自适应布局（目前鸿蒙端为单列布局，横屏体验不如 Android 端）；清理识别出的死代码与未接线的成员。中期最有价值的方向是**微信小程序端**——服务端协议与逻辑层都已就绪，理论上只需重写界面层，这也是课程加分项。此外还可以考虑：单人成绩的防作弊（服务端下发时附带签名与下发时刻，提交时校验"时长不小于服务器记录的题目持有时间"）、更丰富的图案库（从几何图元扩展为图案库或元胞自动机生成）、以及每关历史用时曲线等长期玩法。

## 十、总结

本项目完成了一个**两端原生 + 一个共用服务端**的完整游戏系统：Android 端（Kotlin + Compose）与鸿蒙端（ArkTS + ArkUI）在功能、玩法、界面、数据与协议上保持一致，共用同一个 Python 服务端与 SQLite 数据库，可以实现双端同房网络对战。系统覆盖了课程要求的功能点——网络获取题目、排行榜、网络对战与蓝牙对战、免密登录、游客离线，并额外实现了自动出题与唯一解闸门、每日一题、每日额度、摇一摇重置、音效与背景音乐、离线缓存重玩等。

从工程角度看，收获最大的是三点认识。

**第一，架构分层的价值在"跨平台"这个约束下会被放大。** 把纯算法逻辑与平台 API 彻底分离之后，同一份设计可以指导两套完全不同的技术栈实现，逻辑层可以被单元测试毫秒级覆盖，将来还能复用到第三种平台。项目里所有"双端一致性"的保障措施，本质上都建立在这一点上。

**第二，"平台特性"是最容易踩坑也最值得记录的部分。** 组件复用机制、编译可达性分析、禁用控件的静默行为、编码与工具链的兼容性——这些问题不会出现在教科书里，但会实打实地消耗大量时间。把它们记录成项目文档与自动化脚本，是让经验可以复用的唯一办法。

**第三，测试不是负担，而是把"主观判断"变成"客观约束"的手段。** 项目后期之所以能把"点下一关没反应""按钮点了没反应"这类问题从"靠人肉点击发现"变成"自动断言"，正是因为把导航抽成了纯逻辑并加了测试。两端共 89 项单元测试与 11 组服务端冒烟，最终成了这个作品最可靠的验收依据。

回头看，本项目也走过弯路：一开始尝试的第三方登录因资质限制而放弃，棋盘视口策略反复调整了两轮才找到"整盘适配"的正解，一部分 UI 问题因为缺少自动化测试而在真机上才暴露。但正是这些返工让我们理解了一个朴素的道理——**可用性优先于炫技，一致性要靠机制而不是靠自觉**。这也是本次综合设计最大的收获。
