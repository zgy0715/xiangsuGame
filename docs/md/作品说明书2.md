## 三．选题

### 3.1 系统简介

本作品为 Android 平台的**像素填空（Fill-a-Pix）逻辑解谜游戏**，取材自康思谜题系列。游戏规则：棋盘上部分格子标有数字提示，每个数字表示**以该格为中心的 3×3 区域内需要涂黑的格子数量**（区域越出棋盘边缘的部分不计）。玩家通过纯逻辑推理逐格确定"涂黑"与"留白"，最终把整个棋盘还原成一幅完整的像素画。

系统内置 10 个关卡，图案依次为红心、笑脸、蝴蝶、苹果、小房子、小鱼、星星、皇冠、月亮、火箭，尺寸从 10×10 递进到 28×28，分简单（1 星）、中等（2 星）、困难（3 星）三档难度。每关谜面均经过自研求解器（约束传播 + 回溯）校验，保证**有且仅有唯一解**。

完整功能体系包括：

- **邮箱验证码登录**：不需要用户名密码——输入邮箱获取 6 位验证码，校验通过签发令牌进入首页，首次登录自动注册并引导设置昵称；另有游客离线入口，免登录也能玩全部内置关卡；

- **联网玩法（游戏从网络获取）**：服务端即时生成并校验唯一解的在线题库（按难度分档）、每日一题（全服同题）、单题排行榜（每人最优成绩），以及网络对战（2\~4 人 WebSocket 房间，服务器权威计时与判名次）和蓝牙双人对战（RFCOMM 直连，双端对称仲裁）；

- **顺序解锁**：通关第 N 关解锁第 N+1 关（第 1 关恒解锁）；在线关不参与解锁链；设置页另有"全部解锁"本机开关便于演示；

- **双模式**：自由模式不限时全局计时；限时模式按难度配置 180\~720 秒时限，超时判负、倒计时低于 1 分钟变红警示；

- **棋盘交互**：智能双向涂黑笔（点空白格涂黑、点已黑格清除，起笔第一格决定整笔方向）、留白标记笔、拖动连涂、双指缩放平移、＋/−缩放按钮与复位；

- **笔划级撤销 / 重做 / 重置**：一条拖动笔划或一次批量操作（一键补齐、清除错误格）均合并为一步可撤销操作；

- **四级辅助体系**：显式检查错误（点击才精确标红真正画错的格子，可一键清除）、一键补齐（额度制：每日登录 +2、上限 6、跨日累积）、提示下一步（求解器推导当前盘面可确定的格子并高亮）、参考答案全屏查看；

- **游戏化结算**：通关揭晓完整像素画 + 撒花动画 + 用时统计 + 下一关直达；限时超时弹出失败结算；对局结算展示 🥇🥈🥉 名次与用时；

- **持久化**：通关进度与补齐额度按账号分片本地保存，杀进程重启不丢失；在线关本地缓存，断网可重玩；

- **离线与网络感知**：断网时顶部提示条 + 在线功能降级为可离线用法；服务器地址可在设置页修改并一键测试连接；

- **体验增强**：点击 / 通关 / 错误音效（SoundPool）、摇一摇重置棋盘（加速度传感器）、背景音乐（`res/raw/bgm.mp3`，进程内 MediaPlayer 循环播放，退后台自动暂停，与音效独立开关）；

- **深夜画室主题**：恒定深色界面（夜幕底 + 亮纸棋盘的聚光对比），品牌靛紫 / 湖水青 / 暖金三色体系，渐变 Hero、分段控件、玻璃质感关卡卡贯穿全 app；竖屏手机与宽屏（≥600dp 平板 / 横屏）自适应双布局。

### 3.2 选题理由

1. **规则极简、推理极深**。Fill-a-Pix 的规则一句话就能讲清（3×3 窗口计数），但求解需要综合运用排除法、区域分割、边界推理、计数归约等多种逻辑手段，"易学难精"的曲线非常适合闯关制游戏，也让"算法解题"这一评分点有真正的用武之地——不是摆一个求解器做样子，而是求解结果直接决定关卡质量。

2. **规则理解可被程序严格验证**。Fill-a-Pix 的规则是纯数学约束：提示数字、答案矩阵、解的唯一性都可以被程序精确表达和验证。本项目每关谜面都由求解器证明唯一解，并由单元测试在每次构建时自动重新证明，在线关卡在服务端生成时还要再过一道独立的唯一解闸门——"每道游戏是否确定唯一解"这一评分点不靠人工检查，而是由流水线强制把关。

3. **具备游戏自动生成的完整管线**。实现了"答案像素图 → 提示推导（3×3 窗口计数）→ 贪心去提示（保留唯一解前提下尽量精简）→ 唯一解校验 → 稀疏谜面"的全自动生成链路，Kotlin 端与 Python 端各一套。新关卡的制作成本从"手工设计并人工验证"降低到"画一幅像素图 + 跑一次脚本"，具备评分点 3"能否生成游戏"的完整能力。

4. **结果有画面感，天然适合展示**。数独类谜题的终点是一堆数字，而 Fill-a-Pix 的终点是一幅像素画——通关瞬间棋盘隐藏全部数字、直接呈现完整图案并撒花庆祝，游戏性和答辩演示效果兼备。

5. **工程结构有代表性**。项目体量适中但覆盖面广：算法层（生成与求解）、状态层（笔划 / 双栈）、渲染层（Canvas 自绘）、手势层（多指针识别与过滤）、持久化（SharedPreferences）、主题系统（Material 3 恒定深色）、单元测试（纯 JVM 毫秒级）、开发工具链（Python），是"五脏俱全"的中小型项目，能有效锻炼分层设计与工程化能力。

### 4.3 核心用例

主要角色为**注册玩家**与**游客**。注册玩家主流程：邮箱验证码登录（含"获取验证码 / 校验验证码 / 校验令牌"三个子用例）→ 首页 → 选模式 → 选关卡 → 涂格推理（涂黑 / 清除 / 留白 / 连涂 / 缩放）→ 撤销重做 → （扩展）检查错误 / 一键补齐 / 提示下一步 / 参考答案 → 通关结算 → 解锁下一关；在线侧另有"玩每日一题""浏览在线题库""查看排行榜""创建 / 加入对战房间"四个扩展用例。游客流程：跳过登录直接进入首页，仅玩内置关卡（离线用例），随时可"切换账号"回到登录用例。服务端作为外部参与者提供"发送验证码邮件""校验验证码签发令牌""即时生成并校验关卡""裁决对战名次与计时""聚合排行榜"五个系统用例。核心用例"涂格推理"的主场景为：选中涂黑笔 → 空白格按下（涂黑）→ 拖动经过多格（连续涂黑）→ 抬起（笔划入撤销栈）；扩展场景：按下时第二指落下（取消笔划）、落在已黑格（本笔转为清除方向）、通关或超时后（棋盘冻结仅可查看）。

### 5.3 数据库设计

持久化数据分两侧：**客户端**只存"这个账号在本机玩到哪了"，数据量小、私人性强，用 Android 轻量键值存储 SharedPreferences；**服务端**存账号、令牌、验证码、题库、每日映射与全部通关成绩（跨设备共享、需聚合查询），采用 **SQLite** 关系数据库。以下按概念 / 逻辑 / 物理三层描述。

**（1）概念设计（E-R 模型）**：涉及五个实体、四条联系。实体"用户"（编号、邮箱、昵称、注册时间）；实体"关卡"（编号、名称、难度、行列数、提示矩阵、答案矩阵、来源；服务端生成的在线关编号为负整数，与内置关正 id 天然分区）；实体"通关记录"（记录编号、关卡编号、用户编号、用时、来源 single/race、完成时间）；实体"验证码"（编号、邮箱、码哈希、创建时间、过期时间、已用标记、失败次数）；实体"对战房间"（房号、房主、阶段、题目、起跑时刻、名次表，**全内存不落库**，符合临时对局语义）。联系：用户 ↔ 关卡 **m:n**（通关，属性为用时 / 来源 / 完成时间，"每人最优成绩"即在该联系上按用户分组取 MIN(用时)）；日历日 ↔ 关卡 **1:1**（每日映射，同一天全服同题）；用户 ↔ 令牌 **1:n**（多设备各自持独立令牌，登出或过期即删）；邮箱 ↔ 验证码 **1:n**（同一邮箱仅最新一条有效，重发即作废旧码——验证码属于"尚未证明身份的邮箱"，不直接关联用户，这是本设计最特殊的一点）。E-R 简图如下（正式报告中绘制完整 E-R 图）：

**（2）逻辑设计（关系模式与键值模型）**：服务端关系模式为 Users(<u>user_id</u>, email\*, nickname, created_at)、Tokens(<u>token</u>, user_id, created_at, expires_at)、EmailOtps(<u>otp_id</u>, email, code_hash, created_at, expires_at, used, attempts)、Puzzles(<u>puzzle_id</u>, name, difficulty, rows, cols, clue_json, answer_json, source, created_at)、Daily(<u>daily_date</u>, puzzle_id)、SolveRecords(<u>record_id</u>, puzzle_id, user_id, duration_ms, source, finished_at)。其中 SolveRecords.puzzle_id **刻意不加外键**：对战可由房主选"内置关"发车，而内置关数据固化在客户端 Levels.kt 中、不在服务端 Puzzles 表里，加外键会直接拒绝这些合法成绩入库。客户端键值模型按账号分片（prefs 文件名带 userId 实现多账号隔离）：会话 `xiangsu_auth`（user_id / token / nickname / last_email）、账号进度 `xiangsu_account_<userId>`（`completed_levels` 内置关通关集合、`online_solved` 在线关集合、`fill_quota_used` 已用额度、`last_bonus_day` 上次发奖日历日）、离线缓存 `xiangsu_level_cache`（关卡 id → 整关 JSON）、设备设置 `xiangsu_settings`（服务器地址等）。

**（3）物理设计（存储实现）**：客户端为应用私有目录下按账号分片的若干 XML 文件（`/data/data/com.example.xiangsugame/shared_prefs/xiangsu_auth.xml`、`xiangsu_account_1.xml`、`xiangsu_account_7.xml`、`xiangsu_level_cache.xml`、`xiangsu_settings.xml`），账号进度文件内容为通关 id 集合、在线关集合、一个整数与一个日期字符串。访问策略：AccountStore 以 `MODE_PRIVATE` 打开；写操作一律 `edit().apply()` 异步落盘避免阻塞主线程；读操作在构造时一次性加载并映射为 Compose 可观察状态（mutableStateOf），首页与游戏页直接订阅状态自动重组，无重复 I/O；额度上限（6）与每日奖励（+2）为业务常量，固化在 QuotaLedger 中并由单元测试覆盖。服务端为单个 SQLite 库文件（默认 `server/xiangsu.db`，可用 XIANGSU_DB 环境变量改路径），短连接 + `journal_mode=WAL`（读不阻塞写，适合"边玩边看排行榜"）+ `foreign_keys=ON`；`tokens` 表以 `expires_at > datetime('now')` 过滤过期令牌，`email_otps` 表只存 `sha256(email|code)` 并以 `used`/`attempts` 支撑单次使用与错码封顶，`solve_records` 在 puzzle_id 与 user_id 上建索引支撑"分组取最小值"的排行榜查询。表结构在服务启动的 lifespan 中 `CREATE TABLE IF NOT EXISTS` 建立，并对旧库执行幂等迁移（补 users.email 列并建唯一索引、去掉 solve_records 的历史外键），保证拿旧库直接启动不会失败且老账号数据不丢。

### 5.4 核心算法概要设计

1. **提示推导（答案 → 谜面）**：`clue[r][c]` = 以 (r,c) 为中心的 3×3 窗口内答案涂黑格数量，越界部分不计，复杂度 O(rows×cols×9)。
2. **求解器（谜面 → 解集）**：约束传播 + 回溯的深度优先搜索。传播规则 A：窗口内已涂黑数等于提示值且仍有未定格 → 未定格全部置空；规则 B：提示值减已涂黑数等于未定格数 → 未定格全部涂黑。两规则反复应用至不动点后仍有未定格则分支递归；解数达 2 立即中止（判定非唯一）。
3. **稀疏提示生成（谜面美化）**：从全量提示出发贪心逐个尝试删除，删除后调用求解器校验仍唯一解则保留删除，否则回滚。一轮贪心即可得到大幅精简且唯一解不变的谜面。
4. **笔划机制（交互打包）**：startStroke → strokeCell×N → commitStroke 把一次拖动的 N 个改动聚合为单个 Move.Batch 入撤销栈；cancelStroke（双指落下等异常结束）整体回滚。
5. **在线关卡生成（服务端 generator.py + puzzle_art.py）**：随机像素画（矩形 / 椭圆 / 三角叠加）→ 推导全量提示 → 贪心去提示 → 唯一解校验 → 入库；每日一题以日历日为随机种子，故同一天全服同题且可复现。所有在线关必须过唯一解闸门，保证"每道游戏是否确定唯一解"不因自动生成而失守。
6. **提示下一步（求解器反哺玩家）**：对当前盘面跑一次约束传播，取被规则 A/B 唯一确定的格子作为提示；盘面与答案矛盾时引导先做错误检查。
7. **对战裁决（服务端 rooms.py）**：服务端缓存房主提交的整关 JSON 为校验基准，选手提交时**只比对涂黑掩码**（与 Validator.isSolved 同构，留白标记不参与），名次 = 服务器接收序、时长 = 服务器时钟差值，客户端自报用时一律忽略；蓝牙对局无服务器，改用**双端对称校验**（双方各自校验对方掩码并交换用时，排序规则一致故结论必然相同）。

## 六．详细设计

### 6.1 数据模型

**格子三态**（CellState）以 Int 值存储，便于 IntArray 紧凑表示整盘：UNDECIDED(0) 未决定（暖白纸面）、FILLED(1) 涂黑（深墨紫）、MARKED\_EMPTY(2) 标记确定留白（浅薰衣草底 + 圆点）。

**关卡结构**（Level）：id / name / difficulty(简单★/中等★★/困难★★★) / rows / cols / clueGrid（−1 表示无提示）/ answerGrid / timedLimitSeconds / cluePositions（稀疏提示坐标集）。工厂方法 `Level.fromAnswer()` 接收答案矩阵与提示位置，内部调用 PuzzleGenerator 生成 clueGrid——**谜面是推导产物而非手工数据，天然与答案一致**。

**关卡数据组织**：小图（10×10~~16×16）用 ASCII 字符画~~ ~~`art("X.", …)`~~ ~~定义，直观易改；大图（20×20~~28×28）用 fillRect / fillEllipse / carveEllipse / fillTriangle 程序化作画（如月亮 = 大圆挖去偏置小圆、星星 = 手写五角星）。

### 6.2 棋盘状态与笔划机制（GameBoard）

```
class GameBoard(rows, cols) {
    cells: IntArray                          // 当前棋盘（三态 Int）
    undoStack / redoStack: ArrayDeque<Move>  // 双指令栈

    startStroke()                        // 开笔：暂存本笔改动
    strokeCell(r,c,target): Boolean      // 涂格：目标态相同则跳过，返回是否变化
    commitStroke()                       // 收笔：非空笔划打包 Batch 压栈（清空 redo）
    cancelStroke()                       // 取消：回滚本笔全部改动

    undo() / redo() / reset()            // 标准栈语义；重置可撤销
    applySolution(answer)                // 一键补齐：整批 Batch
}
```

Move 抽象为"一批 (格子下标, 旧值, 新值)"三元组集合：撤销 = 逆序回写旧值，重做 = 正序回写新值。三个设计要点：**一笔一记录**（拖涂 20 格只占一个栈元素，撤销一步整笔回退）；**cancel 与 commit 对称**（手势层任何非正常结束都整体回滚，不留半笔）；strokeCell 返回 Boolean 供界面层驱动版本号，避免无效重组。

### 6.3 求解器（PuzzleSolver）

求解主流程：初始化每格值域 {0,1} → 循环应用传播规则 A/B 至不动点 → 全部确定则记录一个解 → 否则任选未定格分支（假设 1 / 0 递归）→ 解数达到 maxSolutions 提前终止。约束传播先收敛大部分格子，回溯只处理真正歧义区域，28×28 谜面毫秒级出解。`maxSolutions=2` 的模式即"唯一解判定器"，是关卡生成的质量闸门；同时它也是"算法解题"能力的直接体现——给定任意合法谜面，程序都能推出全部解。

### 6.4 校验器（Validator）

三类校验相互独立：`isSolved`（每格 FILLED 状态与答案逐位相等，留白标记不参与——通关判定）；`wrongCells`（仅报"已提交但画错"：FILLED≠答案 1 或 MARKED\_EMPTY≠答案 0，UNDECIDED 永不误报——检查错误）；`satisfiedClues`（提示格窗口无未定格且涂黑数等于提示值——数字变绿反馈）。"错误检查默认不打扰"的设计哲学：平时棋盘不显示任何对错信息（防止变相偷看答案），玩家主动请求时才一次性给出精确结果。

### 6.5 棋盘视图与手势（BoardView）

**渲染**：单 Canvas 自绘整盘（28×28 也只是一次绘制批次）。绘制顺序：格子底色（图片模式墨黑 > 错误红底 > 涂黑 > 留白 > 空白五级分色）→ 留白圆点 → 提示数字（按数值 0\~9 分色、已满足变绿、涂黑格上白字）→ 错误红 ✗ → 网格线（线宽 ÷ viewScale，放大后仍是 1px）→ 装裱外框（随缩放变换）。

**手势**（awaitEachGesture 自定义循环）：awaitFirstDown 等待落下 → **指针类型过滤**（仅 Touch 与鼠标左键进入笔划流程，中键 / 右键 / 触控笔 / 滚轮忽略）→ 单指进入笔划采样循环（移动量超半格步长即换算格子回调 onStrokeCell，快速滑动不断线）→ 第二指落下立即 onStrokeCancel 回滚误涂并切换缩放平移 → 抬起 onStrokeEnd 提交笔划；非交互模式（通关揭晓 / 超时冻结）仅允许查看手势。**缩放体系**：双指捏合（手势中心锚定）+ ＋/− 按钮（视口中心锚定）+ 复位；clampViewOffset 把平移量约束在"棋盘始终覆盖视口"内，杜绝拖飞。指针坐标到格子下标为 O(1) 逆变换。

### 6.6 游戏页状态管理（GameScreen）

界面状态全部为 Compose 可观察对象：boardVersion（Int 计数器，棋盘 Canvas 重组的唯一触发器，避免整页重组）、tool / strokeTarget（当前笔与智能笔整笔方向）、checkedWrong（检查结果，动手即清空）、elapsedSeconds / timedOut（计时与超时）、showZoomed / revealedAnswer（参考答案）。

智能双向笔方向判定：onStrokeBegin 时 strokeTarget 置空，本笔第一格落在黑格则整笔为清除，否则整笔为涂黑——拖动过程方向一致，撤销依然一步整笔。计时用 LaunchedEffect + delay(1s) 协程自增；限时超时置 timedOut 冻结棋盘弹失败卡。响应式布局用 BoxWithConstraints 判定宽 ≥600dp 走"左棋盘（封顶 480dp 居中）+ 右侧 230dp 竖排控制栏"，否则竖排紧凑布局（控件压缩至约 130dp，棋盘最大化）；结算卡 heightIn(max = maxHeight−24dp) + 卡内 verticalScroll，任何屏幕不溢出。

### 6.7 账号进度持久化（AccountStore / QuotaLedger）

AccountStore(context, userId) 用 `xiangsu_account_$userId` 作为 prefs 文件名，同一设备切换账号时各账号的通关集合、额度、在线关记录完全隔离；AppGraph 维护 userId → AccountStore 注册表避免重复 I/O。completedLevels（仅内置关）、onlineSolved（仅在线关负 id，不参与解锁链）、fillQuotaUsed、lastBonusDay 均为 mutableStateOf，首页关卡网格与游戏页额度按钮实时联动；markCompleted 幂等写；pruneCompleted 在账号初始化时清理已删关卡孤儿 id。**每日登录奖励**：额度规则抽成纯对象 QuotaLedger（不碰 SharedPreferences，可直接 JVM 单测），仅在**跨日**时发放 +2（上限 6），同日重复登录或自动续登不重复发放——之所以从"每次登录 +2"改成"每日 +2"，是因为会话持久化后冷启动会自动续登，"每次登录"在真实使用中会退化成形同虚设甚至刷额度。顺序解锁判定 `isUnlocked(id) = id>0 && (id==1 || (id-1) in completed)`；设置页另有"全部解锁"本机开关供答辩演示直接跳关。

### 6.8 登录与会话（AuthManager / LoginRules / ApiClient）

两步式邮箱验证码登录：`requestEmailCode(email)` 先本地校验格式再 `POST /api/auth/send-code`，成功后按服务端返回的 resendAfterSeconds 起倒计时；`loginWithEmailCode(email, code)` 校验码为 6 位数字后 `POST /api/auth/login`，成功即持久化 `Session(userId, token, nickname, email)`，`isNew` 为真时由根导航弹一次昵称引导。**客户端不生成、不持久化任何验证码**——验证码由服务端生成与校验，客户端只提交用户输入并持久化服务端下发的令牌；账号稳定性来自服务端 users 表那一行（邮箱唯一），而不是客户端复用的某个 code（旧版"设备级 mock code"的问题见第九章第 8 条）。LoginRules 把邮箱格式校验、验证码输入过滤（只留数字、截断 6 位）、提交可用性与重发倒计时抽成纯逻辑对象，因此这套规则可在 JVM 直接单测，也保证客户端提示与服务端判定同一口径。ApiClient 用 OkHttp 拦截器在每个请求发出时读取当前令牌注入 `Authorization: Bearer`（登出 / 401 后旧令牌立即失效），`safe{}` 把异常统一映射为可直接展示的文案（网络不可达 / 服务端 {"error": ...} / 401 特殊化为 UnauthorizedException），服务器地址变更后按版本号自动重建 Retrofit 实例。冷启动由 AuthManager.init 读 prefs 恢复会话；游客以 userId = −99、空令牌表示，isGuest 为真时首页隐藏在线入口并展示"游客模式"提示条。服务端验证码只存 sha256(email|code)、10 分钟过期、单次使用、错 5 次作废、60 秒重发间隔与每小时 / 每天发送上限；发信走标准库 smtplib（QQ 邮箱 / 163 授权码），**未配置 SMTP 或投递失败时回退为控制台打印验证码**，保证无外网环境仍可完成登录演示。

### 6.9 对战设计（BattleProtocol / BattleSession / 双传输）

协议与状态机复用同一套代码，只在传输层分叉：`BattleTransport` 接口（connect / send / close）由 NetworkBattleTransport（OkHttp WebSocket → `/ws/rooms/{code}?token=…`）与 BluetoothBattleTransport（Classic RFCOMM 直连，帧以换行分界）分别实现，`BattleSession` 是与传输无关的竞速状态机，帧类型含 roomState / choosePuzzle / start / raceStart / progress / finish / finished / result / rematch / playerLeft / error / ping / timeSync。网络对战流程：服务端建房（4 位房号，剔除易混字符 0O1I）→ 全员连入同一房间 → 房主选题（内置 / 每日 / 随机）→ 服务端缓存题目为基准并广播 raceStart → 竞速中 progress 帧按 0.5 秒节流转发驱动实时进度条 → finish 由服务端比对掩码、按接收序排名、按服务器时钟计时并写榜。**断线重进与重赛**：掉线只标记 connected=False，席位与进度保留；房主掉线保留宽限期（默认 60 秒）等待重连，超时才解散房间；竞速中重进的未完成者会被重发题目并重置进度（本地棋盘已丢）；settled 后房主可 rematch 回到 lobby 清空上局状态。**服务器时钟校时**：客户端与服务器往返 timeSync 帧，按 NTP 思路用往返时延校正得到服务器时刻，竞速计时与名次全部以此为准，改系统时间无法作弊。**蓝牙双人**：主机选题发车，双方各自校验对方答案掩码并按用时排序，双端对称校验保证两端独立算出的胜负结论一致。

### 6.10 视觉主题与共享控件

**深夜画室主题**：夜幕背景 #100E1C + 夜表面卡片 #1B1929，品牌三色（靛紫 #8B7CFF / 湖水青 #5EDDD8 / 暖金 #FFC85C）；棋盘刻意保持亮色纸面，与暗界面形成"聚光"对比突出玩法区；MainActivity 固定 SystemBarStyle.dark 浅色系统栏图标，任何系统外观下观感一致。**Widgets.kt 共享控件**：SegmentedControl\<T>（泛型分段选择器，选中段渐变高亮）、GradientButton（渐变主按钮）、GlassChip（Hero 玻璃胶囊）、NicknameDialog（昵称弹窗），登录 / 首页 / 游戏 / 设置多端复用保证风格统一。**PicturePreview** 把任意答案矩阵渲染为透明底小图（首页谜底、结算揭晓、登录 Hero 装饰通用）。

### 6.11 Python 工具链

三个脚本构成关卡生产线：gen\_clues.py（贪心去提示 + 唯一解校验，输出 Kotlin SparseClues 代码段）；verify\_clues.py（解析 SparseClues.kt 逐关校验唯一解）；gen\_audio.py（合成点击/通关/错误音效）。修改关卡标准流程：改 Levels.kt 图案 → 同步 gen\_clues.py 图案副本 → verify\_clues.py 定位失效关 → gen\_clues.py &lt;关名&gt; 重生成 → 提示集贴回 SparseClues.kt → 单元测试终审。定稿期间用过的 render\_patterns.py / final\_patterns.py（终端字符画核对造型）与 update\_clues.py（自动写回）已删除：它们各自带一份图案副本，且 update 会拿旧快照覆盖线索集。

## 七．系统实现

### 7.1 工程与技术栈

Kotlin 2.2.10 + Jetpack Compose（BOM 统一版本）+ Material 3；Retrofit 2.11 + OkHttp 4.12（REST 与 WebSocket）+ kotlinx-serialization；AGP 9.2.1 / Gradle Kotlin DSL / libs.versions.toml Version Catalog；minSdk 24 / targetSdk 36；服务端 Python 3 + FastAPI + Uvicorn + SQLite（标准库 sqlite3，无 ORM）+ 标准库 smtplib 发信；JUnit 4 纯 JVM 测试与纯 assert 冒烟脚本。

### 7.2 关键功能实现

1. **通关判定与结算**：每次棋盘版本号变化后调用 Validator.isSolved；为 true 时冻结棋盘、切换"图片模式"（隐藏提示数字，直接以答案矩阵渲染，避免留白圆点残留在成品画上）、撒花动画 + 三色渐变描边结算卡（用时、下一关渐变主按钮）。在线关通关额外触发成绩上传（POST /api/leaderboard/submit），失败静默不影响本地通关。
2. **限时模式**：倒计时胶囊常驻 HUD，低于 60s 变红；超时触发 TimeoutOverlay（红描边卡 + 再来一局 / 返回），本局不写通关进度。
3. **一键补齐**：useFill() 扣额度 → applySolution(answer)（单 Batch 可一步撤销）→ 版本号自增；额度为 0 按钮灰化。
4. **检查错误**：wrongCells 返回精确错格集合，Canvas 红底红 ✗ 渲染并显示错误数；"清除错误格"批量回未定（可撤销）；玩家任何动手自动清空过期检查结果。
5. **已满足提示变绿**：每次重组计算 satisfiedClues 集合传入 BoardView，数字按"满足→绿、涂黑格→白字、其余→按数值分色"三级渲染。
6. **拖动连涂**：手势循环按半格步长采样移动事件，途经格子逐个回调 strokeCell；笔划在 commit 前不落撤销栈，快速乱拖也只产生一个可撤销单元。
7. **鼠标环境净化**：起笔处检查 PointerType 与按钮，仅 Touch / 左键放行，拖动循环二次过滤；滚轮事件不消费不缩放，桌面与真机行为一致。
8. **关卡数据**：小图 ASCII 字符画、大图程序化作画；Level.fromAnswer 由答案自动生成全量 clueGrid，再叠加 SparseClues 得稀疏谜面。
9. **邮箱验证码登录**：登录页为两步式状态机（LoginStep.EMAIL / CODE），发码后启动 LaunchedEffect 倒计时协程；验证码输入框在 onValueChange 里过滤非数字并截断 6 位，填满 6 位自动提交；服务端错误文案经 safe{} 原样呈现，用户不需要看错误码。服务端入库前先 sha256(email|code)，校验用 secrets.compare_digest 常量时间比较，消费用 `UPDATE ... WHERE used = 0` 的 rowcount 保证并发下只有一方成功。
10. **游戏从网络获取**：PuzzleRepository 三级缓存（内存 LRU 16 题 → xiangsu_level_cache → 网络），命中即返回，未命中才走 Retrofit；服务端整题接口返回含答案的完整关卡供客户端本地校验，题库列表只回元信息（不含答案矩阵，避免一次拉大包）；每日一题按东八区日历日取题，全服同题。
11. **排行榜**：服务端 compute_board 按 puzzle_id 分组取每人 MIN(duration_ms) 排序（并列时按 user_id 保证名次稳定），compute_my_best 用"比我更快的人数 + 1"反推名次；source 参数区分单人 / 对战榜，两榜独立。
12. **网络对战**：NetworkBattleTransport 用 OkHttp WebSocket 连接 /ws/rooms/{code}，25 秒发一次 ping 保活（服务端 90 秒无消息判掉线）；BattleSession 解析帧驱动 Compose 状态，进度帧 0.5 秒节流；服务端在 finish 帧比对涂黑掩码、按接收序排名、按服务器起算时刻计算时长并写入 solve_records(source='race')。
13. **蓝牙双人对战**：Classic RFCOMM（UUID 固定，主机 listenUsingRfcommWithServiceRecord 等待、从机 createRfcommSocketToServiceRecord 连接）直连，帧以换行分界；结束后双方各自校验对方掩码并交换用时，用同一排序规则独立得出结论。
14. **断网与网络感知**：NetworkMonitor 注册 CONNECTIVITY_ACTION 广播驱动顶部红条；ApiClient 把 IOException 统一映射为"无法连接服务器,请检查网络或设置页的服务器地址"，登录页与在线入口因此都有可读的降级路径。

## 九．遇到的问题、解决办法或改进思路

1. **笑脸嘴角方向错误**：渲染核对发现第 2 关"笑脸"嘴巴画成 ∩ 型（像皱眉）。调整 ASCII 定义两行顺序改为 ∪ 型微笑；图案变化导致原稀疏提示不再唯一解，用 gen\_clues.py 重新生成并写回（31→30 个提示），双端校验恢复唯一解。

2. **月亮孤立杂散像素**：第 9 关月亮（大圆挖偏置圆的程序化作画）在 (5,19)、(19,19) 出现远离月牙主体的孤立像素——大椭圆浮点舍入在边缘填入 0.98<1 的格子，而挖除椭圆在该处 1.03>1 挖不掉。将 carveEllipse 半径 7.5 微调至 7.7 完整覆盖填充边缘后消除，并同步 Python 副本重新生成提示。教训：程序化作画的浮点边界必须显式核对，为此把"改图案必跑 verify_clues.py 唯一解回归 + 单元测试终审"写进工具链标准流程。

3. **图案双源不同步**：Levels.kt（Kotlin）与 gen\_clues.py（Python）各存一份图案，改一处忘另一处时 verify 会拿旧答案校验新提示产生误判。在流程文档固化"改图案必须两处同步 + 单元测试终审"；长期拟让 Python 直接解析 Kotlin 源码，消除副本实现单一数据源。

4. **鼠标滚轮 / 右键误触发笔划**：桌面调试时滚轮滚动会沿滚动方向"涂出一条笔划"。根源是手势层 awaitFirstDown 不区分指针类型，滚轮事件流被当作拖动。在起笔处增加指针类型与左键过滤（仅 Touch / 左键放行），拖动循环二次过滤，并移除实验性的"滚轮缩放"——滚轮一律无响应，桌面与真机行为完全一致。

5. **三支笔切换繁琐**：初版"涂黑 / 留白 / 橡皮"三支笔，涂擦频繁切换。合并为智能双向涂黑笔：起笔第一格决定整笔方向（数独类 App 成熟范式），一支笔覆盖全部单指操作；笔划机制保证方向判定与一步撤销互不干扰。

6. **胜利结算卡小屏溢出**：结算卡内容总高约 500dp，小屏 / 横屏下超出屏幕被裁切，观感像"没居中"。改 BoxWithConstraints + heightIn(max = maxHeight−24dp) 封顶 + 内容 verticalScroll + 像素画宽度自适应，任何屏幕完整居中。

7. **大棋盘格子太小**：20×20 / 28×28 在竖屏手机格子过小（底部控件占约 310dp）。重排控件（撤销/重做/重置改紧凑胶囊、辅助三键并一行）压缩至约 130dp，棋盘增高约 180dp（16×16 格子从约 16dp 提至 21dp）；宽屏自动切"左棋盘 + 右侧栏"双布局。

8. **登录方式：从"微信式一键登录"改为"邮箱验证码"。** 实验要求写的是"不需要用户名密码登录，要求小程序登录"。最初的"微信小程序式授权登录"在无微信资质下能跑通，但本质是自欺：code 由客户端自己编、openid 是 sha1(code) 派生，**服务端从未验证过任何东西**。查证官方文档确认三件事：原生 App 的微信登录走 `sns/oauth2/access_token`（参数 code），而代码里写的 `sns/jscode2session`（参数 js_code）是小程序专用接口，用移动应用 AppID 只会得到 `40013 invalid appid`；Android 端"应用必须通过审核才能调起微信"，且未上架应用微信登录有 100 次/天限制（超限报 `10060`）；客户端"持久化一个 code 反复使用"与真实凭证语义冲突（真实 code 一次性、10 分钟过期，第二次必然 `40163 code been used`）。结论：以个人主体、无企业认证、无已上架应用的资质**无法完成真实微信登录的接入与演示**，保留假登录在答辩中不诚实。最终改为**邮箱 + 6 位验证码**：真实发信（SMTP，QQ 邮箱 / 163 授权码）、服务端校验哈希 / 有效期 / 单次使用 / 频率限制后签发令牌，并保留控制台兜底通道以便离线演示；客户端不再生成与持久化任何凭证，账号稳定性改由服务端 users 表（邮箱唯一）承担。它满足"不需要用户名密码"的原始意图，又把登录做成了真的。

9. **服务端成绩入库被外键拒绝。** 排行榜上线后，用"内置关"发起的对战成绩写不进 solve_records。根源是建表时 puzzle_id 带了指向 puzzles 的外键，而内置关（正 id）的数据固化在客户端 Levels.kt 中、不在服务端 puzzles 表里（该表按约定只存负 id 的在线关），外键直接拒绝了这些合法成绩。去掉该外键（puzzle_id 保留为逻辑引用）并在 init_db 里写一次性迁移：检测到旧表仍带外键时重建表并复制数据。**同类问题**：登录方式改造时给 users 表加 email 列，若把唯一索引写在建表脚本里，旧库启动会因"列不存在"抛 `no such column: email` 导致整个服务起不来；修正为先探测列、ALTER 补列、再建索引，并把迁移写成幂等，最后专门用"构造旧 schema → 启动 → 校验老账号数据仍在"回归验证。教训：外键与迁移顺序都要考虑"线上已有旧数据"这一前提。

10. **改进思路（对接加分项）**：鸿蒙端 / 小程序端可复用纯 Kotlin 的逻辑层与零改动的服务端协议，只需重写界面层；单人成绩目前仍为客户端自报时长（对战已由服务端计时），可让服务端下发题目时附带签名与下发时刻，提交时校验"时长 ≥ 服务器记录的题目持有时间"；随机像素画生成器可从"几何图形叠加"扩展为图案库 + 元胞自动机，配合唯一解闸门批量产出新题；可用 Room 记录每关历史用时曲线做个人趋势与"重刷最速"玩法。

## 十．总结

本项目完成了一款规则严谨、交互流畅、界面完整的 Android 原生 Fill-a-Pix 像素填空解谜游戏，主要结论如下：

**1、以"唯一解"为核心的质量观贯穿全程。** 从需求阶段确立"每关谜面必须算法证明唯一解"的硬约束，形成"提示推导 → 贪心去提示 → 求解器校验 → 单元测试把关"的闭环：每次构建时重新证明 10 关唯一解，Python 脚本从另一侧独立回归，服务端在线关生成同样必经唯一解闸门。这直接回应了康思游戏评分体系中"规则理解是否到位"与"每道游戏是否确定唯一解"两个关键点，也让后续改关（修正笑脸、月亮）有安全网可依赖。

**2、算法能力覆盖"生成"与"求解"两端。** 自研约束传播 + 回溯求解器既是谜面质量闸门，也具备对任意谜面解题的能力；提示推导与稀疏化生成让新关卡制作成本降到"画一幅图 + 跑一次脚本"，具备游戏自动生成管线；同一套求解器还反哺出"提示下一步"，把算法能力直接变成玩家的推理助手。

**3、工程分层带来真实的开发效率。** 逻辑层零 Android 依赖使 59 项客户端测试毫秒级运行；UI 层问题（滚轮误触、结算溢出、棋盘过小）与逻辑层问题（图案缺陷、提示失效）独立定位、独立修复、独立验证。项目中的多次返工（三支笔 → 智能双向笔、滚轮缩放加入又移除、浅色 → 恒定深色主题、假微信登录 → 真邮箱验证码）都是真实使用与调研反馈下的小步迭代，体现"可用性优先于炫技、诚实性优先于好看"的产品判断。

**4、交互细节决定解谜手感。** 笔划机制（一笔一撤销、可取消）、起笔定向智能笔、双指落下自动回滚误涂、滚轮与右键完全净化、错误检查"默认不打扰"——这些细节共同构成"用笔画画"而非"点格子填表"的核心体验，是本作品区别于普通实现的主要特色。

**5、联网能力把单机解谜扩展为多人对抗。** 游戏从网络获取（题库 + 每日一题，服务端即时生成并校验唯一解）、排行榜、网络对战（WebSocket 房间、服务器权威计时与判定）与蓝牙对战（RFCOMM 直连、双端对称仲裁）四项加分项全部落地；"服务器不接受客户端自报成绩"与"在线题必经唯一解闸门"两条约束，让联网能力没有以牺牲公平性与谜题质量为代价。

**6、登录做成了真的。** 最初为满足"小程序登录"要求实现的"微信式一键登录"经调研确认无法以可获得的资质真实接入，且原实现里服务端从未真正验证过任何凭证；最终改为邮箱 + 6 位验证码，真实发信、真实校验、保留离线兜底。这次取舍与随之暴露的旧库迁移问题（第九章第 8、9 条）是本项目在"工程诚实性"上最有价值的一课。

**7、不足与展望。** 单人成绩仍为客户端自报时长（对战已由服务端计时）；鸿蒙端与微信小程序端尚未实现（服务端与协议已为其预留，零改动即可复用）；关卡图案生成器目前限于几何图形叠加。后续按"鸿蒙端 → 成绩防作弊 → 图案库扩充"继续迭代。

通过本项目的完整开发周期（需求 → 设计 → 编码 → 测试 → 文档），小组成员切实掌握了移动应用的分层架构设计、Compose 声明式 UI 与状态管理、Canvas 自绘与手势系统、网络编程（REST / WebSocket / 蓝牙）与服务端开发（FastAPI + SQLite）、轻量持久化与多线程，以及纯 JVM 单元测试与配套工具链建设等工程能力，达到了实验目的的各项要求。
