**踩过的坑(移植时会反复用到)**:

1. `~/.hvigor/project_caches` 里的 `@ohos/hvigor` 是 **junction**,指向旧安装位置(如 `C:\DevEco Studio`)
   会报 `ENOENT ... hvigor.js`;删掉 `project_caches` 重新引导即可。
2. **ArkTS 只编译"被引用到"的文件**:没被任何页面/测试 import 的 `.ets` 不会进编译产物,
   所以 `BUILD SUCCESSFUL` **不代表**新写的库编译过了 —— 必须用单测 import 它们才算验证。
3. ArkTS 限制(移植时反复遇到):
   - 不支持无类型对象字面量(`arkts-no-untyped-obj-literals`),空对象要写 `JSON.parse('null')`;
   - 不支持构造函数参数属性(`constructor(private x: T)`),字段必须显式声明再赋值;
   - enum 不能带字段与方法 → 用查找表 + 自由函数;
   - `preferences` 等 API 声明会抛异常,需 try/catch(否则 WARN)。
4. **ArkUI 与 Compose 的写法差异**(登录页一次踩完):
   - `FontWeight.Black` 不存在 → 用 `FontWeight.Bolder`;
   - 没有 `TextButton` 组件 → 用 `Button(...).backgroundColor(Color.Transparent)`;
   - `InputType.NumberPassword` → `InputType.NUMBER_PASSWORD`(枚举名全大写);
   - `linearGradient` 的 colors 必须是 `Array<[颜色, 位置]>` 元组数组,**不能**写成 `string[][]`;
   - `getContext(this)` / `promptAction.showToast` 已 deprecated(仍可用,后续换 UIContext 版本)。
5. **类型-only 的 import 会被编译期擦除**:`ui/Screens.ets` 里 `Level` 只作类型使用,
   所以 `model/Level.ets` 不进主产物(但会进单测产物)。想确认某文件是否被编译,
   看 `entry/build/default/intermediates/loader_out/default/ets/sourceMaps.map` 的 `sources` 列表。
6. `assembleHap` 与 `test` 是**两套产物**(`build/` 与 `.test/`);改配置后要重跑 `assembleHap` 才能看到
   合并结果,`test` 不会刷新 HAP。

## 0. 三条总体判断(先说结论)

1. **服务端零改动是最大红利。** 现有 FastAPI 服务端的接口(DTO)、WebSocket 帧协议、
   数据库结构都可以原样复用,鸿蒙端只需要「重写客户端」。这条已经在 README 的规划里写明了,
   现在要把它变成现实 —— 因此本项目的工作量集中在**客户端重写**,不涉及后端。
2. **纯逻辑层可以"逐行翻译",不重写算法。** `model/` 下的求解器、校验器、提示生成、
   撤销栈、关卡数据都是纯 Kotlin(无 Android 依赖),翻译成 ArkTS 是机械工作;
   而**关卡数据(10 关图案 + 稀疏提示)必须用脚本从 Kotlin 源码生成**,不能手抄 ——
   手抄必然和 Android 版漂移(这个坑本项目已经踩过一次,见 `作品说明书.md` 9.3)。
3. **建议先收口 Android 版再开始移植。** 目前 Android 侧还有若干已知缺陷未修完
   (启动状态、旋转重建丢状态、计时器、音视频释放等,见审计清单批次 C/D/E)。
   带着 bug 移植 = 把这些 bug 原样复制到鸿蒙版,之后要**修两遍**。
   建议顺序:Android 收口 → 冻结功能基线 → 再按本计划移植。

## 3. 关键工程决策(三个必须提前定的点)

### 决策 1:关卡数据用脚本生成,不手抄

新增 `tools/gen_harmony_levels.py`(沿用 `tools/` 现有做法):

- 输入:`app/src/main/java/.../model/Levels.kt`、`SparseClues.kt`
- 输出:`entry/src/main/ets/model/Levels.ets`、`SparseClues.ets`
- 规则:`answer` 矩阵逐行转成 `number[][]`;`art(...)`/程序化作画(`fillEllipse` 等)
  用与 `puzzle_engine.py` 相同的原语在 Python 侧重算,保证与 Kotlin 结果逐格一致;
  生成后**自检**:每关唯一解 + 唯一解 = 答案(复用 `server/puzzle_engine.py` 的求解器)

**收益**:关卡数据永远与 Android 一致;Android 改图案后重跑脚本即可,不会漂移。

### 决策 2:ArkTS 的"没有 data class / sealed"怎么处理

| Kotlin | ArkTS 写法 |
|---|---|
| `data class Level(...)` | `class` + 构造函数 + 手写 `copy()`(字段不多,可接受) |
| `sealed interface Screen` | `enum ScreenKind` + 一个携带可选参数的 `class Screen` |
| `IntArray` / `Array<IntArray>` | `Int32Array` / `Int32Array[]`(避免 `number[]` 的装箱开销) |
| `Set<Pair<Int,Int>>` | `Set<string>`(键用 `"r,c"`)或 `number[]` 编码,提示集只需查存在性 |
| 扩展函数 | 顶层函数或静态方法 |
| `enum class Difficulty(val label, val stars)` | `enum` + 静态查找表(ArkTS 的 enum 不支持带字段) |

### 决策 3:棋盘绘制层必须重写(但数学复用)

Android 用 Compose `Canvas` + `drawRect/drawText` + 手势 modifier;ArkUI 用
`Canvas` + `CanvasRenderingContext2D`,手势用 `PanGesture` / `PinchGesture` / `GestureGroup`。

- **可复用**:坐标换算(`boardIndexAt`)、视野偏移钳制(`clampViewOffset`)、
  缩放上下限、多指落下即取消当前笔划的判定 —— 这些是纯数学,直接翻译。
- **必须重写**:绘制指令、文本测量(数字居中)、设备像素比处理。

### 4.1 跨端对战验收(为什么这是最强验收点,怎么做)

**为什么必然可行**:服务端只认三样东西 —— Bearer token、4 位房号、JSON 文本帧。
房间状态是服务端内存里的 dict,玩家身份来自 `db.user_by_token(token)`,
服务端**无从区分**、也**不需要区分**客户端是安卓还是鸿蒙。
`server/smoke_test.py` 里那套房间流程测试,用的就是"裸 JSON 客户端"(不是安卓),
本身就证明了"任何会说这套协议的客户端都能玩"。

**四个必须提前验的风险点**(M0/M6 各验一半):

| 风险 | 现象 | 应对 |
|---|---|---|
| 明文 HTTP 策略 | 鸿蒙拒绝 `http://192.168.x.x:8000` | M0 真机验证;必要时配置网络安全策略 |

## 9. 真机首轮问题修复记录(2026-09-17)

### 9.1 邮箱登不上

**现象**:鸿蒙端填邮箱点「获取验证码」登不进去。

**根因(两层,缺一不可)**:

1. **默认服务器地址是安卓模拟器的写法**。鸿蒙端 `LocalSettings.DEFAULT_SERVER_URL` 原来照抄了
   `http://10.0.2.2:8000/` —— `10.0.2.2` 是 **Android 模拟器**里指向宿主机的别名(本质是
   `localhost` 的别名),鸿蒙模拟器/真机不认它,`localhost` 又指模拟器自己。
   👉 必须填**电脑在局域网里的真实 IPv4**(`ipconfig` 看 WLAN/以太网)。
2. **服务端得先用带 SMTP 的脚本启动**。直接 `python -m uvicorn ...` 不会加载 `server/smtp.env`,
   服务端日志会打印 `[mail-fallback] 未配置 SMTP`,邮件根本发不出去(验证码只落在控制台)。

**修法**:

| 改动 | 文件 |
|---|---|
| 默认地址改成开发机局域网 IP,并在注释里写明"鸿蒙不能用 10.0.2.2/localhost" | `harmony/ets/data/LocalSettings.ets` |
| 新增 `HttpClient.ping()` + `AuthManager.testConnection(url)`:请求服务端根路径 `/` 做连通性自检 | `harmony/ets/api/HttpClient.ets`、`auth/AuthManager.ets` |
| 登录页「服务器设置」面板加**「测试连接」按钮**+ 分步提示(ipconfig / 启动脚本 / 先测再存) | `harmony/ets/ui/LoginScreen.ets` |
| 设置页同样加「测试连接」与提示 | `harmony/ets/ui/SettingsScreen.ets` |
| 网络失败文案带上"正在连哪个地址"+ 排查三步 | `harmony/ets/api/HttpClient.ets` |
| `smtp.env` 打开 `XIANGSU_ECHO_CODE=1`:演示模式下验证码直接在 App 里显示,邮件进垃圾箱也不怕 | `server/smtp.env`(本机、不进版本库) |

**本机已实测**(服务端起在 `0.0.0.0:8000`):

```
GET  http://192.168.43.50:8000/            -> 200 {"name":"xiangsu-game-server", ...}
POST http://192.168.43.50:8000/api/auth/send-code  -> 200 {"delivered":false,"devCode":"362202"}
POST http://192.168.43.50:8000/api/auth/login      -> 200 {"userId":9,"token":"...","isNew":true}
```

> 演示口径:开 `XIANGSU_ECHO_CODE=1` 后,登录页第二步会直接显示「演示验证码:xxxxxx」,
> 点一下就能登录 —— 答辩现场不必收邮件。(对外部署记得改回 0。)

### 9.1.1 一条 bat 起服务端(scripts\start-server-smtp.bat)

不用记命令:**双击 `scripts\start-server-smtp.bat` 即可**(也可 `start-server-smtp.bat 8123` 换端口)。
它做四件事:① 检查端口占用并问你要不要清掉;② 读 `server/smtp.env`(空值跳过);
③ 打印脱敏配置 + **本机所有局域网地址(照抄进 App 就行)**;④ 在 `0.0.0.0:<端口>` 起 FastAPI。

启动输出(实测):

```
[config] loaded ...\server\smtp.env (7 keys)
[config] SMTP_HOST = smtp.qq.com
[config] SMTP_PASS = z***************
[config] ECHO_CODE = 1  (demo mode: the app shows the code itself)
[ok] SMTP looks configured - verification emails will be sent for real
[client] fill one of these into the app (Settings / Server):
         http://192.168.43.50:8000/
```

**写这个脚本时踩的两个 Windows 编码坑(值得记进报告)**:

1. `smtp.env` 是 UTF-8 **无 BOM**,Windows PowerShell 5.1 的 `Get-Content` 会按系统 ANSI
   (中文机器上是 GBK)解码 → 中文注释变乱码、行尾残留 `\r` 让 `StartsWith('#')` 判断失真,
   **整行 `XIANGSU_ECHO_CODE=1` 被当成注释吞掉**。修法:改用
   `[System.IO.File]::ReadAllLines($path, [Text.Encoding]::UTF8)` 显式按 UTF-8 读。
2. **`.ps1` 自身必须存成 UTF-8 with BOM**:PS 5.1 读无 BOM 的 UTF-8 脚本同样按 GBK 解析,
   非 ASCII 字符(破折号 `——`)直接导致 `Unexpected token '}'` 语法错误。改完先用
   `[System.Management.Automation.Language.Parser]::ParseFile()` 验语法再跑。


### 9.2 填涂背景不一致(棋盘四周一圈白/黑,像没铺满)

**现象**:棋盘区域底色与页面不统一,填涂时能看出"格子外面还有一块别的颜色"。

**根因**:旧 `BoardView` 用 `Math.min(宽向, 高向)` 定格子边长 —— 画布比棋盘"胖"或"瘦"时,
棋盘只在画布中间占一小块,**四周留白**(画布背面是白色),看着就是一圈白边/黑边不一致。
另外 `clearRect()` 把画布擦成透明,露出的又是容器底色。

**修法**(`harmony/ets/ui/BoardView.ets` 重写):

1. 整张画布先铺成**页面同色**(`#100E1C`),棋盘之外不再出现第二种底色;
2. 格子边长改用 `max(宽向, 高向)` —— 纸面**铺满**画布,宁可溢出也不留边;
3. 进入关卡自动按**整盘适配**定基准缩放(`fitZoom`),纸面在画布内居中,周边均匀留夜幕色;
4. 配色与安卓端 `BoardView.kt` **逐个色值对齐**(纸面 `#FAF9FF`、涂黑 `#37324F`、
   留白标记 `#E9E5F7`、格线 `#E2DDF1`、错误红 `#D32F2F`),两端口径一致。

> ⚠ **第 2 条后来被推翻了**:`max(宽向, 高向)` 会让大棋盘溢出视口边界(见 9.4.1)。
> 最终实现按安卓端口径:**格子边长 `min(视口宽/列, 视口高/行)`**,整盘恒定完整可见;
> 画布仍然先铺页面同色,所以纸面居中时四周是均匀的夜幕色,不会再有白边。

### 9.3 格子里的数字太小看不清

**现象**:棋盘格中的提示数字糊成一团(28×28 的大棋盘尤其明显)。

**根因**:① 字号固定 `0.44 × 格子边长` 且下限只有 8px,手机上一格才 11vp 时数字只有 ~5px;
② 没有自动放大,25×25 以上的棋盘一进关就"必须捏合才能玩"。

**修法**:

1. 字号系数 `0.44 → 0.52`,下限 `8 → 10`,并加 **22px 上限**(小棋盘不会变成巨字);
2. **一进关自动适配**:`fitZoom = min(画布宽/(列数×基准格), 画布高/(行数×基准格))`,
   大棋盘自动放大到铺满屏幕宽度,**不用先捏合就能看清数字**;

> ⚠ 这条也在 9.4.1 被推翻:最终不做"自动放大到溢出",而是**1× = 整盘适配**,
> 想看清楚靠双击 2× / 双指放大查看(与安卓端一致)。
3. 数字按大小分色(0 灰 / 1-2 蓝 / 3-4 青 / 5-6 紫 / 7+ 红),已满足转绿,涂黑格上转白
   —— 与安卓端 `clueColor()` 一致,可读性再上一层;
4. 新增**双击放大/还原**与右上角「⤢ 整盘」按钮(放大后出现),一键回到全貌。

**验证**:`tools/sync_harmony.py`(9 文件)+ `hvigorw assembleHap` → `BUILD SUCCESSFUL in 43 s`,
退出码 0,只剩既有的 deprecated 警告。

> ⚠ 仍需要你确认的:字号/缩放是"我按屏幕尺寸算出来的合理值",**真机观感还得你看一眼**。
> 如果还嫌小,直接告诉我"再大一档",我调 `0.55`/`24` 这两个数即可。

### 9.4 第二轮真机反馈:棋盘太小

**现象**:进去看棋盘只有屏幕中间一块,格子里的数字也小。

**根因**:格子上限 `CELL_BASE_MAX` 只有 34,且底色/工具行占了不少竖向空间;字号下限也偏低。

### 9.4.1 第三轮反馈:按钮挡棋盘 + 预览器涂得慢 + 大棋盘溢出边界

**问题一:右下角「整盘 / 1:1」两个按钮挡住了格子(严重)。**

**问题二:关卡变大后棋盘顶出边界(严重)。**

**问题三:鸿蒙预览器里涂黑特别慢。**

> 问题一、二是同一个根因:**我在鸿蒙端自己发明了"铺满(让棋盘溢出视口)"的视口模型**,
> 用 `max(宽向, 高向)` 定格子边长。小棋盘看着"填满"了,关卡一大(20×20 以上)
> 内容就超出边界;还额外放了两个常驻按钮去补救,结果挡住格子。
> **教训:视口语义没有"创新"空间,应该逐条对齐安卓端。**

**修法:视口模型完全照安卓 `BoardView.kt` 重写**(`harmony/ets/ui/BoardView.ets`):

| 安卓端 | 鸿蒙端(现在) |
|---|---|
| 1× = 整盘适配,格子 = `min(视口宽/列, 视口高/行)` | 同:1× 恒定整盘可见,**永不越界** |
| `MinZoom = 1f`,`MaxZoom = 12f` | 同:`zoom ∈ [1, 12]` |
| `clampViewOffset` 按**分量各自比较**,未放大恒为 0(居中) | 同:`originX()` 里 `contentW <= canvasW` 就居中,否则钳制 `[视口-内容, 0]` |
| 放大后(`> 1x`)右上角才出现「复位」 | 同:仅 `zoom > 1.05` 时显示「复位」,未放大不显示、不挡格子 |
| 双指缩放/平移 + 右下角 +/− 按钮(≥200 格) | 双指缩放/平移 + **双击 = 1× ⇄ 2×**(不放常驻按钮,避免遮挡) |
| 字号 `max(格宽,格高) × 0.46`,按测量结果居中 | 同:`× 0.46` + 手机可读下限 9vp;`textAlign/textBaseline` 居中 |

顶栏副标题同步改成同口径的 **`难度 · 行×列 · 一格 xx.x vp`**(取 `min(宽向, 高向)`),
看不清时把这个数报出来即可,不用猜。

**问题三的根因(三处叠加)与修法**:

1. **每涂一格都重绘整个棋盘**,而 `ctx.font = ...` + `fillText` 逐格画数字是 canvas 里最贵的操作
   (28×28 就是 784 次文字排版)
   → **静态层缓存**:纸面 + 网格 + 数字预渲染到 `OffscreenCanvas`,
   用 `transferToImageBitmap()` 拿 `ImageBitmap` 缓存,之后每帧只做**一次 `drawImage`**;
   注意 ArkTS 里它是**同步**返回(写成 `.then()` 会编译不过);离屏不可用时自动退回直画;
2. 网格原来是**逐格 `strokeRect()`**,路径数 `2N²` → 改成每行/每列一条线,**`2N² → 2N`**;
3. 空白格也在逐格 `fillRect` → 动态层**只画有状态的格子**。

另外 ArkTS 类型坑:`OffscreenCanvasRenderingContext2D` 与 `CanvasRenderingContext2D` 是两个类型,
写联合类型会让 `fillStyle` 赋值报类型不匹配 —— 参数声明成 `object` 再在函数内断言即可。

本机实测:`hvigor BUILD SUCCESSFUL`,`entry-default-unsigned.hap` 4.95 MB,退出码 0。
**预览器帧率我这边测不了**:如果还慢,把顶栏那行"一格多少 vp"和你用的机型/设备告诉我。

### 9.4.2 第四轮反馈:鼠标点击涂黑没反应

**现象**:鸿蒙端用鼠标点格子,涂不上色。

**根因:单指涂色本来就不该交给手势系统。**

1. `PanGesture` **必须有位移**才会触发 —— 鼠标点一下不动,`onActionStart/Update/End`
   一次都不回调,表现就是"点了没反应"(安卓端直接读指针 down/move/up,落下即落笔,所以没这问题);
2. 补 `TapGesture(count: 1)` 理论可行,但**预览器里的鼠标点击不一定被手势识别器接受**;
3. 多个 `.gesture()` 叠加还有优先级与竞争问题,很难排查。

**修法:改用 `onTouch()` 直接读触摸/鼠标事件,与安卓端的指针处理同构**
(`harmony/ets/ui/BoardView.ets`):

| 事件 | 行为(与安卓一致) |
|---|---|
| `TouchType.Down` | 落笔:touchBegin + 涂第一格 |
| `TouchType.Move` | 沿轨迹连涂(**同一格的重复事件直接丢弃**,不白重绘) |
| `TouchType.Up` | 提交(整笔 = 一步撤销);`Cancel` → 取消本笔 |
| `touches.length >= 2` | 取消当前笔划并让 `PinchGesture` 接管缩放(防误涂) |
| 350ms 内第二次落下且落点相近 | 1× ⇄ 2× 缩放(自己判时间差,不依赖 TapGesture) |

`PinchGesture` 只保留"双指 = 缩放/平移"一个职责。这样单指/鼠标完全不经过手势识别器,
**预览器、模拟器、真机三种环境行为一致**。

### 9.4.4 第六轮反馈:按键静默失效 + 数字仍偏小

**问题一:"个别按键按了没反应"(用户追问:会不会还有别的键也这样)。**

**根因(一条会连坐多处的写法)**:**ArkUI 的 `enabled(false)` 完全不响应点击** ——
没有回调、没有 toast、没有视觉反馈,用户看到的就是"这个键坏了"。

最典型的是游戏页操作行:撤销/重做/补齐被改成 `.enabled(canUndo())` 之类,
而**进关时撤销栈本来就是空的** → 一点反应都没有;补齐额度用完后同理。
另外那一行塞了 **6 个按钮**(每个约 60vp),中文标签被截断、手指也难点中。

**修法(定成一条规矩)**:

> **除非禁用理由对用户可见(倒计时、加载中),否则不要用 `enabled(false)`。
> 无效时应当:按钮照旧可点 → 给出具体原因的 toast。**

落实的地方:

| 位置 | 之前 | 现在 |
|---|---|---|
| 撤销 / 重做 | `enabled(栈非空)`,空栈静默 | 可点;空栈提示「没有可撤销/可重做的操作」 |
| 一键补齐 | `enabled(额度>0)`,用完静默 | 可点;用完提示「次数已用完(每日登录 +2)」 |
| 对战「加入房间」 | `enabled(房号 4 位)`,不足静默 | 可点;提示「请输入 4 位房号,例如 A3KP」 |
| 对战「④ 发车」 | `enabled(已选题且≥2人)`,不满足静默 | 可点;分别提示「先选一道题再发车」「至少要有 2 人在线才能发车」 |
| 对战「创建房间」 | `enabled(!busy)` | 可点;建房中提示「正在建房,请稍候…」 |
| 游戏页操作行 | 一排 6 个按钮(约 60vp/个) | **拆成两排、每排 3 个**;高度 34→38vp、字号 11→12 |
| 检查结果条「清除/关闭」 | 高 28vp | 34vp(热区过小) |
| 首页「切换账号」 | 高 26vp | 32vp |

**并写了审计脚本 `tools/audit_buttons.py`** 做全仓排查,报告四类问题:
`E1` 用了 `enabled` 的按钮(需人工确认禁用理由是否对用户可见)、`E2` 没有 `onClick` 的按钮、
`E3` 非 Button 组件挂 `onClick`(热区不明确)、`E4` 一排按钮过多或热区 <32vp。

本次结果:全仓 **16 处 `enabled`** 中,只有上述 **3 处属于"静默失效"**,其余都是倒计时/加载中
这类对用户可见的合理禁用;另外修掉 2 处热区过小。`E2`(没有 onClick 的按钮)为 **0**;
全屏遮罩(s 通关卡、放大查看)都在 `if` 条件下,不会误挡点击。

**问题二:棋盘数字仍偏小。**
安卓端用 `max(格宽, 格高) × 0.46`、下限 9vp —— 手机 28×28 的盘面上只有 ~5px。
鸿蒙端放宽为 **`× 0.60`、下限 12vp、上限 30vp**(提示窗最多 3 列,60% 已接近可读上限)。

### 9.5 鸿蒙工程一键脚本(DEVxiangs\scripts\)

在 `harmony/scripts/` 下维护、由 `tools/sync_harmony.py` 同步进 DevEco 工程(源码托管在本仓库,
改完一条命令同步,不用手改工程里的副本)。**双击即可,不需要打开 DevEco 的构建菜单**:

| 脚本 | 作用 |
|---|---|
| `check-env.bat` | 环境自检:DevEco / SDK / node / hvigorw / hdc 是否找到、有没有连设备、本机局域网 IP、现有 HAP |
| `build-hap.bat` | 清理 + 编译出 HAP(可加 `--fast` 只增量编译) |
| `run-hap.bat` | 安装到设备/模拟器并启动(可加 `--launch` 只启动) |
| `log-hap.bat` | 看设备日志(等价于 Android 的 logcat;`--all` 看全部) |
| `start-server.bat` | 转调 `xiangsuGame\scripts\start-server-smtp.bat`(两端共用一个服务端) |

`hvigor-run.ps1` 是它们的公共实现(必须存成 **UTF-8 with BOM**;`sync_harmony.py` 会
自动给 `.ps1` 补 BOM、给 `.bat` 去 BOM,免得 cmd/PowerShell 的编码坑再次出现)。

**写这套脚本踩的坑(很有代表性,值得写进报告)**:

1. **hvigor 守护进程会崩**:报 `00306056 Specification Limit Violation` / 提示
   `nodeOptions.maxOldSpaceSize` —— 之后每次构建都失败。脚本默认加 `--no-daemon` 绕开。
2. **`pause` 会永久挂住**:从非交互宿主(脚本/CI)启动 `.bat` 时,`pause` 等不到按键,
   窗口永远不返回 —— 表现就是"编译卡死"。改成 `timeout /t 8` 倒计时,想看就设 `KEEP_OPEN=1`。
3. **PowerShell 的集合"标量退化"**:`New-Object ArrayList` / 自定义函数返回值在
   **只有一个元素**时会被折成标量(布尔),后续 `.Add()` 直接报
   `[System.Boolean] does not contain a method named 'Add'`,日志表现为"只剩一行 True"。
   解法:用强类型泛型列表 `List[string]` 并内联解码,不抽函数、不走管道。
4. **`cmd /c` 会吃掉带空格路径的引号**:`"D:\DevEco Studio\..."` 被拆成 `""D:\DevEco`。
   改用 `Start-Process -RedirectStandardOutput` 让 hvigorw 自己写日志文件。
5. **`$ErrorActionPreference='Stop'` + 原生命令写 stderr** = PowerShell 把 WARN 升级成
   致命错误,明明 `BUILD SUCCESSFUL` 也判失败。
