# 答辩提纲 · 像素填空(Fill-a-Pix)双端 + 服务端

> 一页纸：技术栈 → 目录 → 三个重点 → 演示顺序 → 必答问题 → AI 使用声明。
> 详细内容见 `作品说明书3-最终版.md`，本文只用于现场翻。

## 一、一句话介绍

康思类逻辑解谜游戏：按数字线索推理涂黑格子、还原像素画。**两端原生客户端（Android / HarmonyOS）+ 一个共用服务端**：服务端负责账号、出题（每题唯一解）、成绩与对战裁决，两端共用同一套协议，可同房竞速。

## 二、技术栈

| 端 | 技术选型 | 关键点 |
|---|---|---|
| Android | Kotlin 2.2 + Jetpack Compose + Material 3 | compileSdk/targetSdk 36、minSdk 24；棋盘用 Canvas 自绘；OkHttp/Retrofit + WebSocket；SharedPreferences 持久化；SoundPool/MediaPlayer |

| 服务端 | Python 3.13 + FastAPI + Uvicorn | 数据库用**标准库 sqlite3**（单文件 + WAL，零额外依赖）；smtplib 发验证码；WebSocket 房间对战；内存房间状态 |
| 数据库 | SQLite | 6 张表（users / tokens / puzzles / daily / solve_records / email_otps）；email 唯一索引、成绩按题目与用户建索引、排行榜用 `RANK()` 窗口函数 |
| 测试 | 两端单测 + 服务端冒烟 | Android **59 项 / 8 类**、鸿蒙 **30 项 / 4 类**、服务端 **11 组**冒烟（自建临时库、可重复运行） |
| 工具链 | Python 脚本 + PowerShell / bat | 关卡生成与唯一解校验、鸿蒙数据同步、双端符号一致性审计、docx 与示意图生成 |

## 四、三个重点(现场就讲这三个)

**1. 算法:唯一解是硬闸门。** 出题器走"先画图 → 再去提示 → 再验解":从全提示开始逐个删,每删一个就重新校验唯一性,直到再删就破坏唯一解;枚举时**搜到两个解即停**（只需判定唯一性）。求解器用约束传播（窗口内已涂满则剩余全留白；已涂数 + 未定数等于提示值则全涂黑）+ 分支回溯,并带解数上限、时间上限、玩家盘面硬约束。点"提示"是同步操作,因此改**两级限时**:300 ms 只做传播,不够再用 1500 ms 完整求解,都超时给降级提示 —— 最坏阻塞 1.8 秒。

**2. 架构:逻辑层零平台 API。** 同一份设计支撑两套技术栈:纯算法与数据模型不引用任何 Android/鸿蒙 API,因此能被单测毫秒级覆盖、可复用到第三种平台。对战再把"传输"与"状态机"分开:`BattleTransport` 抽象 + `BattleSession` 状态机,于是 WebSocket 与蓝牙 RFCOMM **复用同一套帧协议与竞速逻辑**。

**3. 一致性机制:靠机制,不靠人盯。** ① 关卡数据用脚本一次性生成并逐关自检（图案逐行一致 / 提示集唯一解 / 唯一解等于答案）;② 协议字段级对齐,服务端不区分平台,冒烟测试里有"裸 WebSocket 客户端"从外部证明;③ 只读符号审计脚本按文件配对抽取两端函数/常量名做差集,快速筛出"鸿蒙端少实现了什么";④ 两端测试同口径,一端逻辑分叉对应测试就红。

> 能打开就讲 2 分钟的代码：`PuzzleSolver.kt`、`BattleSession.kt` + `BattleProtocol.kt`、`BattleIdentity.kt`；鸿蒙端 `BoardView.ets`（位图缓存 + 网格按行列画线）、`ScreenStack.ets`（导航抽成纯逻辑加测试）。

## 五、演示顺序(从稳到险,5 分钟)

1. 登录:邮箱 + 6 位验证码（30 秒）→ 2. 内置关玩到通关揭晓（讲三态与判定函数）→ 3. 在线题库 / 每日一题 / 排行榜 → 4. 网络对战:两台同房、发车、实时进度、结算（讲服务器权威计时）→ 5. 蓝牙对战 + 鸿蒙端同房（备录屏）。

**兜底**：服务器不可用就切"游客进入"跑单人与蓝牙;网络演示不稳就直接跳第 5 步并放录屏。演示前确认:服务已启动、手机与电脑同一热点、两台真机蓝牙已配对。

## 六、必答问题

| 问题 | 一句话答法 |
|---|---|
| 唯一解怎么保证? | 出题时逐个删提示并重验,枚举搜到两个解即停;不通过就整题作废重新生成 |
| 提示为什么不会卡? | 两级限时(300 ms 传播 / 1500 ms 完整)+ 超时降级,最坏 1.8 秒 |
| 对战怎么防作弊? | 网络:名次与用时由服务器裁决,客户端自报只用于展示,帧白名单过滤;蓝牙:不采信对端自报用时,用本机单调时钟;纯 P2P 挡不住"拿到答案后秒提交",已如实说明 |
| 鸿蒙为什么没有蓝牙? | 经典蓝牙 SPP/RFCOMM 与机型强相关,课程周期内无法保证现场稳定演示;跨端同房走网络,协议共用,不影响"双端同房"这一验收点 |
| 两端一致性靠什么? | 数据脚本生成 + 协议对齐 + 符号审计脚本 + 两端同口径测试 |
| 数据库为什么用 SQLite? | 单机演示零依赖、WAL 够用;重点是索引与窗口函数的用法,而不是选型堆料 |

## 七、AI 使用与个人创作的边界(建议主动说)

**用 AI 加速的环节**：样板与重复代码、API 用法查证、报错信息翻译、文档与图表排版、测试脚手架、跨平台机械搬运、只读审计脚本。

**由我判断并负责的环节**：选题与玩法、架构分层与数据模型、协议与算法取舍（唯一解闸门 / 两级限时 / 服务器权威计时 / 蓝牙对称仲裁）、真机问题的定位与修复决策、验收演示与讲解。

**证据链**：`git log`（提交信息带因果与日期）、两端单测与服务端冒烟报告、双端一致性审计清单、真机问题记录（说明书第九章）。

**说法模板**："这块我用 AI 加速了 X，但 Y 这个判断是我做的，理由是 Z，代价是 W。"
不要含糊说"全是我写的"（追问即破），也不要说"AI 写的我不清楚"（等于放弃工程能力）。
